# Контракт: REST API сервера (v1)

Связано: D-34, D-36, D-37, `spec/06-data-server.md`, `spec/08-sharing.md`, `spec/09-agents-api.md`. Типы TS: `packages/shared/src/contracts/api.ts`. Подробная схема (OpenAPI) генерируется сервером из кода и публикуется по `GET /v1/openapi.json`.

## Общее

- База: `https://<host>/v1`. JSON, UTF-8. Двоичные поля — base64url без padding.
- Аутентификация: `Authorization: Bearer <accessToken>` (короткоживущий, 15 мин) + `refreshToken` (30 дней, ротация при каждом обновлении). Повторное предъявление уже использованного `refreshToken` — признак кражи: устройство отзывается. Исключение (уточнение 2026-10-26, предложение потока ios-core, принято координатором): повтор в течение **60 с** после обмена (ответ потерялся в сети), пока выданный взамен токен ещё не использован, возвращает **тот же** новый `refreshToken` (и свежий `accessToken`) — запрос идемпотентен. Повтор позже или после использования нового токена — отзыв устройства, как раньше.
- **Отзыв устройства (2026-10-27).** Любой запрос с access-токеном отозванного устройства и `POST /auth/refresh` с его refresh-токеном получают `401 { "error": { "code": "device_revoked", "message", "reason" } }`. `reason`: `user` (отключено в списке устройств или `logout`), `password_change` (пароль сменили на другом устройстве), `recovery` (восстановление по ключу восстановления), `token_reuse` (повтор использованного refresh-токена), `account_deleted` (аккаунт удалён — приходит на запросы с ещё не истёкшим access-токеном; refresh-токены удаляются вместе с аккаунтом, и `/auth/refresh` после этого отвечает обычным `401 unauthorized`). Только по `device_revoked` клиент **стирает локальные данные**; неизвестное или отсутствующее значение `reason` при этом коде считается отзывом с `reason: "user"` (совместимость с будущими причинами), а 401 без такого тела (обычный `unauthorized`, страница прокси) — только обновление токена или вход, без стирания (`classifyApiFailure`, векторы `api/failures.json` в `@datascratch/shared`). Истёкший или неверный токен, сбой сети — обычный `401 unauthorized` без `reason`: обновить токен и повторить. Старые клиенты, не знающие `device_revoked`, видят просто 401: refresh тоже не проходит, и они просят войти снова — данные при этом не стираются (безопасная деградация).
- Ошибки: HTTP-код + тело `{ "error": { "code": string, "message": string } }`. Коды: `bad_request`, `unauthorized`, `device_revoked` (401, с полем `reason`, см. «Аутентификация»), `forbidden`, `not_found`, `conflict`, `rate_limited`, `payload_too_large`, `internal`. У `rate_limited` (429) есть необязательное `retryAfterMs` — через сколько повторить. Превышение квоты хранения аккаунта — `payload_too_large` с сообщением `storage quota exceeded` (в REST — `413`, в синхронизации — `error` с `ref` = `clientMsgId`).
- Идентификаторы создаёт клиент (UUIDv7); повторный `POST` с тем же id и тем же содержимым — идемпотентен (`200`), с другим — `409 conflict`.

## Аутентификация (D-34, `crypto.md`)

| Метод | Путь | Тело → ответ |
| --- | --- | --- |
| POST | `/auth/prelogin` | `{ email }` → `{ salt, kdf }` (для неизвестного email — детерминированная фальшивая соль, чтобы нельзя было перебирать адреса) |
| POST | `/auth/signup` | `{ email, salt, kdf, loginKey, recoveryLoginKey, wrappedMasterKeyPassword, wrappedMasterKeyRecovery, userId, accountDocId, inviteCode? }` → `Session`. `403`, если регистрация на сервере закрыта или нужен код приглашения (`DS_SIGNUP`); любой конфликт — один и тот же `409` (аудит безопасности 2026-10-27). При открытой регистрации — не больше `DS_SIGNUP_DAILY_LIMIT` новых аккаунтов за сутки (по умолчанию 100), сверх — `429 rate_limited`; новый аккаунт получает свою квоту хранения `NEW_USER_STORAGE_QUOTA_BYTES` (по умолчанию 1 ГБ, не больше общей `USER_STORAGE_QUOTA_BYTES`), админ поднимает её командой `ds quota <почта> <ГБ>` (проверка безопасности 2026-11-02) |
| POST | `/auth/login` | `{ email, loginKey, deviceName }` → `Session` |
| POST | `/auth/refresh` | `{ refreshToken }` → `Session` |
| POST | `/auth/logout` | `{ refreshToken }` → `204` |
| POST | `/auth/recovery/start` | `{ email, recoveryLoginKey }` → `{ recoveryToken, wrappedMasterKeyRecovery, userId }` |
| POST | `/auth/recovery/finish` | `{ recoveryToken, salt, kdf, loginKey, wrappedMasterKeyPassword }` → `Session` |
| POST | `/auth/password` | (авторизован) `{ currentLoginKey, salt, kdf, loginKey, wrappedMasterKeyPassword }` → `204` |
| POST | `/auth/recovery-key` | (авторизован) `{ currentLoginKey, recoveryLoginKey, wrappedMasterKeyRecovery }` → `204` — новый ключ восстановления (`crypto.md` §4): старый перестаёт работать сразу, незавершённые восстановления отменяются, другие устройства остаются в системе |

`Session = { userId, deviceId, accessToken, refreshToken, accessExpiresAt, wrappedMasterKeyPassword, accountDocId }`. В `signup` и `recovery/finish` можно передать необязательное `deviceName` (уточнение потока server).

## Блокноты и документы (D-36)

| Метод | Путь | Тело → ответ |
| --- | --- | --- |
| POST | `/notebooks` | `{ notebookId, mode: "private"\|"agent", wrappedKey (notebookKey под masterKey), notebookKey? (только для mode=agent) }` → `Notebook` |
| GET | `/notebooks` | `Notebook[]` |
| GET | `/notebooks/:id/key` | `{ wrappedKey }` |
| PATCH | `/notebooks/:id/mode` | `{ mode, notebookKey? }` — включение режима «для агентов» передаёт ключ, выключение — удаляет серверную обёртку |
| DELETE | `/notebooks/:id` | удаляет блокнот и все его документы |
| POST | `/docs` | `{ docId, kind: "account"\|"notebook"\|"note", notebookId \| null }` → `204`; регистрация до первого `push` |
| PATCH | `/docs/:id` | `{ notebookId }` → `204` — перенос заметки (`kind = note`) в другой блокнот того же пользователя; повтор с тем же `notebookId` — `204` |
| DELETE | `/docs/:id` | окончательное удаление (после корзины) |
| GET | `/docs/:id/versions` | список снимков для истории версий `{ seq, createdAt, deviceId, authors: Author[] }[]`; `authors` — авторы правок с прошлой версии: сервер запоминает их при сохранении снимка по обновлениям после предыдущего снимка (без повторов, по порядку первой правки, D-54) |
| GET | `/docs/:id/versions/:seq` | `{ payload }` — зашифрованное состояние на момент `seq` |

`Notebook = { id, mode, createdAt, wrappedKey, shared }` (`shared` — у блокнота есть участники, D-54).

`Author = { kind: "user", userId } | { kind: "guest", shareId } | { kind: "agent", tokenId }` — автора ставит сервер по тому, кто прислал обновление, а не со слов клиента (D-54). У гостя `shareId` — **не id ссылки**, а непрозрачный устойчивый id в формате UUIDv7 (`sha256("ds-guest-author|" + shareId)`): id ссылки сам по себе даёт гостевой токен, поэтому никогда не уходит клиентам (проверка безопасности 2026-11-02).

**Перенос заметки** (`PATCH /docs/:id`, 2026-10-25). Сервер меняет только блокнот документа; содержимое, история версий, вложения и `noteKey` остаются прежними. Порядок на клиенте: (1) обернуть `noteKey` ключом нового блокнота (`ad = ds1|key|note|<noteId>`) и записать `NoteMeta` в индекс нового блокнота; (2) `PATCH /docs/:id`; (3) удалить `NoteMeta` из индекса старого блокнота. Отдельно передавать ключ серверу не нужно: для блокнотов «для агентов» сервер получает `noteKey` из `NoteMeta.wrappedKey` индекса, а ключ блокнота у него есть (`crypto.md` §8). Права следуют за заметкой сразу: гости шеринга старого блокнота её теряют (подписчики получают `error doc_not_found` с `ref = docId`), шеринг самой заметки сохраняется; агенты видят заметку, только если новый блокнот «для агентов» и входит в их разрешение. Ошибки: `400` — документ не заметка; `404` — нет документа или целевого блокнота у пользователя.

Прочие типы ответов (уточнение 2026-10-25, предложение потока core):

- `Device = { id, name, createdAt, lastSeenAt, current: boolean }`;
- `Share = { id, target: { kind, id }, permission, expiresAt, createdAt }`;
- `AgentToken = { id, name, notebookIds, permission, expiresAt, createdAt, lastUsedAt }` (без секрета; секрет только в ответе на создание).

| PUT | `/attachments/:id/chunks/:index` | тело — двоичный кусок (`application/octet-stream`) → `204` |
| GET | `/attachments/:id` | `{ size, chunkCount, mime, uploadedChunks: number[] }` (для докачки) |

Лимит размера вложения — 200 МБ (настраивается).

**Картинка по ссылке (D-52, 2026-10-27):** `POST /fetch-image` — тело `{ url }` → `200` с байтами картинки (`Content-Type` — тип картинки, `Content-Length`) или `422 { error: "blocked" | "not_image" | "too_large" | "timeout" | "unreachable" }`, `429` при превышении частоты. Только для вошедшего; ограничения сервера — в `decisions/0052-image-fetch-proxy.md` (частные сети запрещены, ≤ 3 переадресаций, только картинки без SVG, ≤ 20 МБ, 15 с, адреса не журналируются). Клиент шифрует полученные байты и загружает как обычное вложение. Уточнение потока server: `Content-Type` ответа определяется по сигнатуре файла (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/heic`, `image/avif`); `429` также приходит, когда сервер уже скачивает много картинок одновременно, — повторить через несколько секунд.

## Совместный доступ по аккаунтам (D-54)

Простой вариант: блокнот или одна заметка, конкретному аккаунту по почте, роли `editor` («Может редактировать») и `viewer` («Только чтение»). Доступом управляет только владелец. Ключи — `crypto.md` §10. `:kind` в путях — `notebook` или `note`.

**Ключи аккаунта**

| Метод | Путь | Тело → ответ |
| --- | --- | --- |
| PUT | `/me/box-key` | `{ publicKey, wrappedSecretKey }` → `204`; один раз на аккаунт (повтор с теми же данными — `204`, с другими — `409`) |
| GET | `/me/box-key` | `{ publicKey, wrappedSecretKey }` или `404`, если пары ещё нет |
| GET | `/users/:userId/public-key` | `{ userId, publicKey }` — только для аккаунтов, связанных с вызывающим общим ресурсом или **принятым** приглашением; иначе `404`, неотличимый от «нет такого аккаунта» (перебор не работает) |

**Приглашения**

| Метод | Путь | Тело → ответ |
| --- | --- | --- |
| POST | `/invitations` | `{ invitationId, target: { kind, id }, email, role }` → `204`. **Ответ одинаковый**, есть аккаунт с такой почтой или нет. Только владелец ресурса. Повтор для той же почты и ресурса заменяет роль и продлевает срок |
| GET | `/invitations?target=<kind>:<id>` | исходящие по ресурсу: `{ id, email, role, status: "pending"\|"accepted"\|"declined"\|"expired", createdAt, expiresAt }[]` |
| DELETE | `/invitations/:id` | владелец отзывает непринятое приглашение → `204` |
| GET | `/invitations/incoming` | входящие: `{ id, target: { kind, id }, from: { userId, email }, role, createdAt, expiresAt }[]` (только `pending`) |
| POST | `/invitations/:id/accept` | → `SharedItem` (ключ ещё может быть `null`, см. ниже) |
| POST | `/invitations/:id/decline` | → `204` |

- Приглашение живёт **30 дней**. Приглашение на почту без аккаунта ждёт регистрации с этой почтой и появляется во входящих после неё. Ссылка «скопировать и отправить» — `https://<web-host>/invite/<invitationId>`: она только открывает программу на входящих, сама по себе прав не даёт.
- Ограничение частоты: не больше **50 приглашений в сутки** на приглашающего (`429 rate_limited` с `retryAfterMs`); `accept` и `decline` — под обычным лимитом авторизованных запросов. `POST /invitations` отвечает одинаково и за одинаковое время, есть аккаунт или нет: поиск аккаунта выполняется в обоих случаях.
- Название блокнота или заметки сервер не знает (оно зашифровано), поэтому во входящих — кто пригласил, что (блокнот или заметка) и роль. Название появляется после принятия, когда клиент владельца выдаст ключ.

**Участники**

| Метод | Путь | Тело → ответ |
| --- | --- | --- |
| GET | `/members/:kind/:id` | `Member[]` — видят владелец и участники; участник, которого владелец ещё не пустил (аккаунт создан после приглашения, ключа нет), видит только себя |
| PATCH | `/members/:kind/:id/:userId` | `{ role }` → `204` (только владелец) |
| DELETE | `/members/:kind/:id/:userId` | `204`. Владелец убирает участника; участник указывает себя — «Выйти». После этого сервер сразу закрывает доступ и ставит `keyRotationPending` |
| PUT | `/members/:kind/:id/:userId/key` | (только владелец) `{ version, wrappedKey }` → `204` — выдать ключ участнику (`crypto.md` §10.2); `409`, если `version` не текущая |
| POST | `/members/:kind/:id/rotate` | (только владелец) смена ключа, `crypto.md` §10.3: `{ version, ownerWrappedKey, previousKeyWrap, memberKeys: { userId, wrappedKey }[], notebookKey? }` → `204`. Атомарно; `409`, если `version` ≠ текущая + 1 или `memberKeys` не совпадает ровно с участниками `active` (с ключом текущей версии): лишний (`awaiting_key`) или недостающий — `409`. Участники `awaiting_key` остаются такими и получают ключ новой версии через `PUT …/key` с новой `version` — так аккаунт, созданный после приглашения, не получит ключ без подтверждения владельца. `ownerWrappedKey` — новый ключ под мастер-ключом владельца (блокнот, `ad` с версией) или под ключом его блокнота (заметка, как в `NoteMeta.wrappedKey`). `notebookKey` — только для блокнота в режиме «для агентов» (сервер переоборачивает его своим ключом, `crypto.md` §8) |
| GET | `/members/note/:id/key` | (только владелец) `{ version, ownerWrappedKey, keyChain }` — текущий ключ отдельно расшаренной заметки. При запуске клиент владельца сверяет `NoteMeta.keyVersion` своих расшаренных заметок с `version` и, если в индексе старее, дописывает `NoteMeta` (на случай сбоя между `rotate` и `push`) |
| POST | `/members/:kind/:id/rotate/done` | (только владелец, `kind = notebook`) все заметки блокнота получили новые ключи → снимает `keyRotationPending`. Для `kind = note` флаг снимает сам `rotate` |
| GET | `/shared-with-me` | `SharedItem[]` |
| GET | `/shared-by-me` | `SharedByMeItem[]` — всё, чем поделился вызывающий (он владелец, и есть участник или непринятое приглашение): по нему клиент владельца при запуске выдаёт ключи, меняет ключ и чинит `NoteMeta`, и по нему же строится окно «Поделиться» (согласовано координатором, 2026-10-27) |

- `Member = { userId, email, role, status: "active"\|"awaiting_key", joinedAt, accountCreatedAfterInvite: boolean }`. `awaiting_key` — приглашение принято, клиент владельца ещё не выдал ключ: он делает это сам, как только оказывается в сети, и затем видит участника `active`. `accountCreatedAfterInvite` — аккаунт зарегистрирован уже после приглашения. Почта при регистрации не подтверждается, поэтому такому участнику клиент владельца ключ сам **не** выдаёт: сначала спрашивает владельца «<почта> приняла приглашение — открыть доступ?» (решение владельца продукта, 2026-10-27, D-54). Остальным ключ выдаётся без вопроса.
- `SharedByMeItem = { target: { kind, id }, keyVersion, keyRotationPending: boolean, pendingSinceVersion: number | null, members: number, awaitingKey: number }`: `members` — участники без владельца, включая `awaiting_key`; `awaitingKey` — сколько из них приняли приглашение, но ещё без ключа.
- `SharedItem = { target: { kind, id }, owner: { userId, email, publicKey }, role, keyVersion, wrappedKey: string \| null, keyChain: string[], docIds: string[], addedAt, agentsMode? }`. `agentsMode` — ресурс читают агенты владельца (значок ✨, только для показа; участник режим не меняет): у блокнота — `mode = "agent"`, у отдельно расшаренной заметки — режим блокнота владельца, в котором она лежит (предложение потока server, 2026-10-28). Старые серверы поле не отдают — значка нет. `keyChain` — звенья цепочки от текущей версии назад (`crypto.md` §10.3). `docIds` — документы ресурса (индекс и заметки блокнота или одна заметка).
- `GET /notebooks/:id/key` у владельца дополнительно отдаёт `{ version, keyChain, keyRotationPending, pendingSinceVersion }`;
- **`pendingSinceVersion`** (согласовано с потоком server, 2026-10-27) — версия ключа в момент, когда `keyRotationPending` стал `true`; без флага — `null`. Сервер ставит его, когда уходит участник с ключом (удаление, выход, удаление его аккаунта); если флаг уже стоит, значение не меняется. `rotate` блокнота без стоящего флага (добровольная смена ключа) ставит флаг сам, с `pendingSinceVersion` = прежняя версия. `rotate/done` и `rotate` заметки сбрасывают его в `null`. По нему любое устройство владельца понимает, где прервалась смена ключа: `version = pendingSinceVersion` — шаг 1 ещё не сделан, `version > pendingSinceVersion` — остались ключи заметок и `rotate/done` (`crypto.md` §10.3); `Notebook` получает поле `shared: boolean`.
- В ресурсе не больше **50 человек**, считая непринятые приглашения: сверх — `409 conflict` с сообщением `member limit`.
- **Всё общее принадлежит владельцу.** Документы и вложения общего ресурса, в том числе созданные участником (`POST /docs` от `editor` регистрирует документ на владельца), считаются в квоту владельца и удаляются вместе с его аккаунтом.
- **Права участников по REST** (кроме синхронизации, `sync-protocol.md` §6):
  - `viewer`: `403` на `POST /docs`, `PATCH /docs/:id`, `DELETE /docs/:id`, `POST`/`PUT`/`DELETE /attachments…`; чтение вложений и версий разрешено;
  - `editor`: создаёт заметки в общем блокноте (`POST /docs` — только `kind = note` и `notebookId` этого блокнота, иначе `403`), загружает и удаляет вложения любой заметки этого блокнота (сервер проверяет документ → блокнот → членство), кладёт заметки в корзину и достаёт из неё (это поле `trashedAt` в индексе — обычная правка); окончательное удаление (`DELETE /docs/:id`) и перенос заметки из общего блокнота (`PATCH /docs/:id`) — `403`, это может только владелец (после переноса в свой личный блокнот участники заметку теряют);
  - гостевые ссылки (`/shares`) на общий ресурс создаёт и отзывает только владелец; `PATCH /notebooks/:id/mode` и `DELETE /notebooks/:id` — тоже.
- **Агенты** (поправка D-54, владелец 2026-10-28): если владелец включил режим «для агентов» у общего блокнота, токены агентов **участника** получают к нему доступ с правами участника: `editor` — чтение и запись, `viewer` — только чтение (запись — `forbidden`). Нового переключателя нет; блокнот появляется в списке блокнотов агентов участника (страница согласия, форма токена, `list_notebooks`, поиск), а если у токена есть список блокнотов — только когда он в этом списке. Автор правок — `{ kind: "agent", tokenId }` токена участника (в истории — «агент <участник>»); заметки, созданные агентом участника, принадлежат владельцу и идут в его квоту. Агент участника не может вынести заметку из общего блокнота в свой (это может только владелец). Доступ заканчивается сразу: владелец выключил режим, убрал участника, участник вышел; участник, ждущий подтверждения владельца, доступа не получает. Отдельно расшаренные заметки агентам участника недоступны. При `rotate` блокнота в режиме «для агентов», удалении и выходе участника сервер сбрасывает кэш ключей агентов (`crypto.md` §8).
- **Удаление аккаунта участника** убирает его членство во всех ресурсах и ставит им `keyRotationPending`, как при выходе.
- Режим «для агентов» у общего блокнота включает и выключает только владелец (`PATCH /notebooks/:id/mode` — `403` для участника).
- Удаление блокнота или заметки владельцем закрывает доступ всем участникам; удаление аккаунта владельца — тоже.

**Уточнения потока server (реализация D-54, 2026-10-27):**

- `POST /invitations`: `409`, если у владельца ещё нет пары ключей (`PUT /me/box-key`); `400` — приглашение самому себе; `409 already a member` — человек уже участник (это владелец видит и в списке участников, существование аккаунта не раскрывается). Повтор для той же почты переносит приглашение на новый `invitationId` (по нему и ссылка); лимит 50 человек он не меняет, если прежнее приглашение ещё действует. Лимит 50 в сутки считает новые приглашения, повторы — нет.
- `POST /invitations/:id/accept`: `409`, если у приглашённого нет пары ключей — владельцу не для кого обернуть ключ. Повторное принятие того же приглашения — `404` (оно уже не `pending`). `DELETE /invitations/:id` — только `pending`, иначе `404`.
- **Подтверждение владельцем** (open-questions, D-54): участник с `accountCreatedAfterInvite = true` до выдачи ключа (`PUT …/key`) не получает ничего — в `SharedItem` `docIds = []`, синхронизация отвечает `doc_not_found`. Выдача ключа и есть подтверждение; доступ открывается сразу, в том числе в уже открытом соединении.
- `Member.status = "active"`, когда у участника ключ текущей версии; иначе `awaiting_key`. В `SharedItem.wrappedKey` — `null`, пока ключа текущей версии нет.
- `rotate` блокнота ставит `keyRotationPending = true` до `rotate/done` (на случай сбоя между шагами). `memberKeys` — ровно участники `active` (ключ текущей версии); лишний или недостающий — `409`. Флаг смены ставится, только если у ушедшего участника был ключ.
- `GET /shared-by-me`: в список входят и ресурсы с `keyRotationPending` без участников (убрали последнего — ключ всё равно нужно сменить, ссылки пересоздать), до `rotate/done` или `rotate` заметки; «непринятое приглашение» — `pending` и не истёкшее; `awaitingKey` — участники без ключа текущей версии (в том числе ждущие подтверждения владельца).
- `GET /members/note/:id/key` — `404`, пока ключ заметки не менялся: версия 1 есть только в `NoteMeta`.
- Изменения участия (роль, удаление, выход, подтверждение) доходят до открытых соединений синхронизации сразу: потерянные документы получают `error doc_not_found`, новая роль действует со следующей записи.
- `GET /docs/:id/versions` и `/versions/:seq` доступны и участникам (обоим ролям). Обновления, записанные до D-54, получают автора по устройству (владелец или агент); у старых правок гостей автора нет.

## Общие пространства (D-62)

Согласовано координатором 2026-11-03. Пространство становится общим ресурсом вида `space`: участники, роли, приглашения, выдача ключа, смена ключа и ответы — те же, что у блокнота в «Совместном доступе» выше, с `:kind = space` в путях `/members/:kind/:id…` и `target: { kind: "space", id }` в `/invitations`, `/shared-with-me`, `/shared-by-me`. Ключи — `crypto.md` §11.

**Пространства**

| Метод | Путь | Тело → ответ |
| --- | --- | --- |
| POST | `/spaces` | `{ spaceId, wrappedKey }` → `Space` — сделать пространство общим: `wrappedKey` — ключ пространства под мастер-ключом (`crypto.md` §11.1). Только для своего пространства; повтор с тем же `spaceId` — `409`. Документ пространства (`kind = space`) регистрируется обычным `POST /docs` с `notebookId = null` до первого `push` |
| GET | `/spaces` | `Space[]` — общие пространства, где вызывающий владелец или участник (с ключом или без) |
| GET | `/spaces/:id/key` | владелец: `{ version, wrappedKey, keyChain, keyRotationPending, pendingSinceVersion }`; участник — ключ приходит в `SharedItem` (`/shared-with-me`) |
| GET | `/spaces/:id/notebooks` | `{ notebookId, version, spaceWrappedKey, keyChain, mode }[]` — блокноты пространства и обёртки их ключей ключом пространства (владелец и участники с ключом текущей версии) |
| PUT | `/spaces/:id/notebooks/:notebookId` | (только владелец) `{ version, spaceWrappedKey }` → `204` — перенести свой личный блокнот в общее пространство (`crypto.md` §11.3); обёртка мастер-ключом удаляется. `409`, если `version` не текущая версия ключа блокнота; `409`, если у блокнота есть свои участники D-54 |
| POST | `/spaces/:id/notebooks/:notebookId/move-out` | (только владелец) `{ version, ownerWrappedKey, previousKeyWrap, notebookKey? }` → `204` — вынести блокнот в личное пространство со сменой ключа (`crypto.md` §11.3; дальше — шаги 2–3 смены ключа блокнота) |
| POST | `/spaces/:id/rotate` | (только владелец) `{ version, ownerWrappedKey, previousKeyWrap, memberKeys: { userId, wrappedKey }[], notebooks: { notebookId, version, spaceWrappedKey, previousKeyWrap, notebookKey? }[] }` → `204`. Атомарно; `409`, если версия пространства ≠ текущая + 1, `memberKeys` не совпадает ровно с `active` участниками или `notebooks` — не ровно все блокноты пространства, каждый с версией текущая + 1 |
| POST | `/spaces/:id/rotate/done` | (только владелец) все заметки всех блокнотов получили новые ключи → снимает `keyRotationPending` у пространства и его блокнотов |
| DELETE | `/spaces/:id` | (только владелец) удаляет пространство, все его блокноты и документы |

- `Space = { id, ownerUserId, keyVersion, keyRotationPending, pendingSinceVersion, createdAt }`. Название, иконка и порядок — в документе пространства (сервер их не видит).
- `POST /notebooks` получает необязательное `spaceId`: блокнот общего пространства; `wrappedKey` тогда — ключ блокнота под ключом пространства (`crypto.md` §11.2). Создаёт владелец или `editor`; блокнот принадлежит владельцу пространства (квота — его). `viewer` — `403`.
- `Notebook` получает `spaceId: string | null`; у блокнота общего пространства `wrappedKey` — обёртка ключом пространства, а не мастер-ключом.
- **Права** участников пространства на блокноты и документы пространства — те же, что у участника общего блокнота (выше, «Права участников по REST», и `sync-protocol.md` §6), на все блокноты пространства сразу, включая новые. Дополнительно `editor` создаёт блокноты (`POST /notebooks` со `spaceId`) и регистрирует документ пространства не может — его регистрирует владелец; в документ пространства `editor` пишет (порядок и названия блокнотов), `viewer` — нет. Удалить блокнот пространства (`DELETE /notebooks/:id`), включить режим «для агентов», вынести блокнот — только владелец.
- `SharedItem` с `target.kind = "space"`: `wrappedKey` — ключ пространства для участника (§11.1), `docIds` — документ пространства, индексы и заметки всех его блокнотов. Блокноты пространства **не** приходят отдельными `SharedItem`.
- Блокнот общего пространства нельзя расшарить отдельно (`/invitations` с его `notebookId` — `409`). Заметки — по ссылке гостям, как раньше; приглашение на отдельную заметку пространства — тоже `409` (она и так видна всем участникам).
- Лимит — 50 человек на пространство, считая непринятые приглашения.
- Удаление аккаунта владельца удаляет его общие пространства; удаление аккаунта участника — как выход.
- Агенты участника — как в поправке D-54: блокноты пространства, открытые владельцем агентам, видны агентам участника с его ролью.

**Уточнения (координатор и поток server, 2026-11-03):**

- Операции D-54 над **блокнотом общего пространства** — `409`: `POST /members/notebook/:id/rotate`, `PUT /members/notebook/:id/:userId/key`, `GET /members/notebook/:id` (своих участников у такого блокнота нет; ключи его меняет `/spaces/:id/rotate`). `POST /members/notebook/:id/rotate/done` — только для блокнота вне пространства (в том числе после `move-out`). `PATCH /notebooks/:id/mode` — владелец пространства, как обычно.
- **Перенос заметки** (`PATCH /docs/:id`) между блокнотами **одного** общего пространства — владелец и `editor` (у обоих есть оба ключа); из пространства наружу и внутрь — только владелец пространства.
- **Флаги смены ключа:** уход участника ставит `keyRotationPending` (и `pendingSinceVersion`) **пространству**; шаг 1 (`/spaces/:id/rotate`) ставит флаг каждому блокноту пространства, чтобы шаг 2 доделывался по блокноту; `/spaces/:id/rotate/done` снимает флаг у пространства и всех его блокнотов. В `/shared-by-me` — пространство (`kind = space`) со своим флагом, его блокноты отдельными элементами не приходят.
- **`docIds`** в `SharedItem` пространства: документ пространства, затем по каждому блокноту — его индекс и его заметки.
- **`GET /spaces/:id/notebooks`** отдаётся владельцу и любому участнику, принявшему приглашение, при любой версии его ключа: обёртки без ключа пространства ничего не раскрывают, а во время смены ключа участник иначе потерял бы список блокнотов.
- **`DELETE /spaces/:id`** удаляет документ пространства, все его блокноты с документами, приглашения и участников; подписанным уходит `doc_not_found`.
- Схемы (`packages/shared`) добавляет поток core; до них сервер может валидировать локальными схемами по этому разделу.
- `GET /notebooks/:id/key` для блокнота общего пространства — `409` (ключ — из `GET /spaces/:id/notebooks`; клиенты отличают такой блокнот по `Notebook.spaceId`).
- `POST /notebooks` со `spaceId` несёт и `spaceKeyVersion` — версию ключа пространства, которым обёрнут ключ блокнота; не текущая — `409` (блокнот, созданный во время смены ключа пространства, иначе остался бы под старым ключом). Клиент при `409` берёт новый ключ пространства и повторяет.
- Участник, ждущий подтверждения владельца (аккаунт создан после приглашения), на `GET /spaces/:id/notebooks` получает `404`.
- `move-out` ставит блокноту `keyRotationPending = true` и `pendingSinceVersion` = прежняя версия: шаги 2–3 доделываются, как у смены ключа блокнота D-54 (`POST /members/notebook/:id/rotate/done`).
- Прерванная смена ключа пространства: шаг 1 сделан, если `Space.keyVersion > pendingSinceVersion`; тогда — ключи заметок всех блокнотов и `rotate/done`.
- Запись доверия: `invite|space|…`, `member|space|…`, `key|space|<id>|<v>`; версии ключей блокнотов пространства — по-прежнему `key|notebook|<id>|<v>` (граница отката каждого). `SharedItem` пространства, владелец которого — сам участник или которое есть в его `account.spaces`, не принимается.

## Уведомления об изменениях аккаунта (D-62)

После перечисленных вызовов сервер шлёт всем устройствам затронутых аккаунтов `account_changed` по сокету синхронизации (`sync-protocol.md` §4, §6; только клиентам с `protocol: 2`). Уведомление уходит после фиксации изменения: клиент, который сразу перечитает, его увидит. Опрос по таймеру остаётся запасным путём (старые клиенты, оборванный сокет).

## Голос (D-65)

Диктовка и запись разговоров с ИИ-обработкой текста (`decisions/0065-voice.md`). Ключи сервисов — только на сервере: клиенты шлют аудио и текст сюда, сервер вызывает распознавание (ElevenLabs Scribe v2, запасное — AssemblyAI) и текстовую модель (OpenRouter). **Аудио и текст проходят через сервер в памяти и не сохраняются и не пишутся в журналы** — в журнал только размеры, длительность, модель и коды ошибок (ПРЕДЛОЖЕНО, D-65). Схемы TS — `packages/shared/src/contracts/voice.ts` (`@datascratch/shared/voice`).

| Метод | Путь | Тело → ответ |
| --- | --- | --- |
| POST | `/voice/transcribe` | `multipart/form-data`: `audio` — файл (`audio/mp4`/m4a, `audio/webm`, `audio/ogg`, `audio/wav`; до **200 МБ** и до **3 ч**), `mode` = `dictation` \| `conversation`, `speakers?` — подсказка числа говорящих 1–8 (только для разговора), `language?` = `ru` (по умолчанию) \| `auto` → `{ durationSec, turns: [{ speaker: "S1", start, end, text }] }` |
| POST | `/voice/text` | `{ task: "clean" \| "minutes" \| "format", style?: "document" \| "plan" \| "minutes" \| "article" \| "letter" \| "notes" (только для `format`, по умолчанию `document`), profanity?: "soften" \| "keep" (по умолчанию `soften`), quality?: "standard" \| "best" (по умолчанию `standard`), turns? \| text? }` → `{ markdown, model }` |
| GET | `/voice/me` | `{ enabled, monthlyMinutes, usedMinutes, resetsAt, isAdmin }` — свой доступ к голосу и квота текущего месяца (UTC); `isAdmin` — администратор ли аккаунт сервера (показывать ли экран `/admin/voice` в вебе, без пробного запроса и `403`) |
| GET | `/admin/voice` | (только администратор сервера) `{ month: "ГГГГ-ММ", resetsAt, accounts: [{ userId, email, name, enabled, monthlyMinutes, usedMinutes, costUsd }], totals: { usedMinutes, costUsd } }` — все аккаунты сервера и итоги месяца (UTC); `costUsd` — стоимость распознавания и текста за месяц |
| PUT | `/admin/voice/:userId` | (только администратор сервера) `{ enabled, monthlyMinutes }` → `204` — включить или выключить голос аккаунту и задать месячную квоту минут |

- **Расшифровка.** `turns` — реплики по порядку; `speaker` — `S1`, `S2`, … в порядке первого появления (идентификаторы сервиса вида `speaker_0` сервер переводит). `start`/`end` — секунды от начала записи. У диктовки один говорящий `S1`. Пустая запись — `turns: []`.
- **Обработка текста.** Ровно одно из `turns` (расшифровка) или `text` (черновик или текст заметки). `clean` — чистая расшифровка, `minutes` — итог разговора, `format` — «Оформить» в выбранном виде (`style`; для других задач `style` — `400`). `profanity` — смягчить (по умолчанию) или оставить ненормативную лексику; `quality: "best"` — «Лучшее качество». Подсказки модели собирает сервер из `@datascratch/shared/voice` (`buildVoiceTextPrompt`); правила — в D-65. Ответ `markdown` — Markdown заметки Datascratch (как у агентов, `agents-api.md` §4); `model` — модель, которая его написала (для истории заметки). Ограничения: `text` и сумма текстов `turns` — до 400 000 символов, `turns` — до 20 000 реплик.
- **Ошибки:** `403 voice_disabled` — голос для аккаунта не включён; `429 voice_quota` — исчерпана месячная квота минут распознавания (с `retryAfterMs` до начала следующего месяца по UTC); `413 voice_too_long` — файл больше 200 МБ или запись длиннее 3 ч; `400 bad_request` — неизвестный тип файла или неверные поля; `502 voice_upstream` — внешний сервис ответил ошибкой (после попытки запасного); `503 voice_unavailable` — голос на сервере не настроен (нет ключей) или временно выключен.
- **Доступ и квота (D-65, решение владельца).** Управляет администратор сервера (`/admin/voice`; кто администратор — настройка сервера; другим — `403 forbidden`). Экран управления — **только в вебе**. Квота — на аккаунт, в минутах распознавания за календарный месяц **по UTC**; по умолчанию 600 минут владельцу и 120 остальным разрешённым аккаунтам (`DEFAULT_VOICE_MONTHLY_MINUTES`), администратор меняет их на экране; `usedMinutes` считает длительность распознанных записей (`durationSec`), обработка текста квоту не тратит. Изменение доступа или квоты аккаунта сервер сообщает его соединениям синхронизации: `account_changed` с `what` = `["voice"]` (`sync-protocol.md` §4) — клиент перечитывает `GET /voice/me`.
- **Подсветка результата.** Текст, вставленный голосом в заметку, клиент помечает меткой `agentEdit` с `agentId = "voice"` (D-10, `document-model.md` §4.2) и подписью «Голос» — как правки агента; снимается, когда пользователь принял текст. Тело — как у всех ошибок (`{ error: { code, message } }`).
- **Первое использование.** Клиент предупреждает, что для голоса запись и текст проходят через сервер и внешние сервисы в открытом виде (исключение из сквозного шифрования, D-65), и просит согласия; запоминает его в настройках аккаунта.
- **Хранение.** Сам сервер ничего не хранит. Аудио разговора клиент сохраняет в заметке обычным зашифрованным вложением (`/attachments`, `crypto.md` §6) и блоком `audio` (`document-model.md` §4.2).
- `account_changed`: добавлено значение `voice` (см. «Доступ и квота»); остальное не меняется.
