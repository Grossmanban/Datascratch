# Контракт: шифрование (v1)

Связано: D-04, D-09, D-34, R-02, R-10, `spec/07-encryption.md`. Реализация TS: `packages/shared/src/crypto/`. Библиотека — **libsodium** на всех платформах (`libsodium-wrappers-sumo` в TS, `swift-sodium` в iOS).

## 1. Иерархия ключей

```
пароль ──Argon2id──► 64 байта ─┬─► loginKey (32) ──► на сервер (сервер хранит Argon2id(loginKey))
                               └─► passwordKey (32) ─ никогда не покидает устройство
                                        │ оборачивает
recoveryKey (32, показывается 1 раз) ─┐ ▼
                                      └► masterKey (32, случайный, создаётся при регистрации)
                                              │ оборачивает
                                              ▼
                                        notebookKey (32, случайный, на блокнот)
                                              │ оборачивает
                                              ▼
                                        noteKey (32, случайный, на заметку)

Режим «для агентов»: notebookKey дополнительно оборачивается serverKey (KMS сервера).
```

- `account`-документ шифруется **masterKey**; `notebook`-документ — **notebookKey**; `note`-документ — **noteKey**; вложения — **noteKey** заметки, к которой прикреплены.
- Ключ отдельной заметки нужен для шеринга одной заметки по ссылке без раскрытия всего блокнота.

## 2. Вывод ключей из пароля

- `crypto_pwhash` с `ALG_ARGON2ID13`, `opslimit = 3`, `memlimit = 64 MiB` (67 108 864 байт), длина выхода 64 байта.
- Вход: пароль в UTF-8 после нормализации **NFKC**. Соль — 16 случайных байт, создаётся при регистрации и хранится на сервере (выдаётся `POST /v1/auth/prelogin`).
- Выход: байты 0..31 — `authSeed`, 32..63 — `passwordKey`.
- `loginKey = crypto_generichash(32, message = "ds1|login", key = authSeed)` (BLAKE2b с ключом).
- Параметры KDF хранятся вместе с солью (`kdf: { alg: "argon2id13", ops: 3, mem: 67108864 }`), чтобы их можно было повысить в будущем.
- **Границы параметров на клиенте (аудит 2026-10-27):** клиент принимает `kdf` из `prelogin` только если `alg = argon2id13`, `3 ≤ ops ≤ 10` и `64 MiB ≤ mem ≤ 256 MiB`; иначе вход и регистрация отклоняются с ошибкой «сервер прислал небезопасные параметры». Иначе враждебный сервер (адрес сервера вводится пользователем, D-49) мог бы занизить параметры, получить дешёвый для перебора `loginKey` и подобрать пароль. Повышение параметров в будущем — вместе с поднятием верхней границы в клиентах.

Сервер хранит `Argon2id(loginKey)` со своей солью (обычное хэширование пароля на сервере). Узнать `passwordKey` по `loginKey` невозможно (разные независимые выходы).

## 3. Формат шифротекста (конверт)

```
байт 0      версия = 0x01
байты 1..24 nonce (24 случайных байта)
далее       crypto_aead_xchacha20poly1305_ietf_encrypt(plaintext, ad, nonce, key) (шифротекст + 16 байт тега)
```

Ассоциированные данные (`ad`, UTF-8) привязывают шифротекст к месту, чтобы его нельзя было подменить другим:

| Что шифруется | `ad` |
| --- | --- |
| Обновление/снимок документа | `ds1|doc|<docId>` |
| Awareness | `ds1|awareness|<docId>` |
| Обёрнутый masterKey паролем | `ds1|key|master|password|<userId>` |
| Обёрнутый masterKey ключом восстановления | `ds1|key|master|recovery|<userId>` |
| Обёрнутый notebookKey мастер-ключом | `ds1|key|notebook|<notebookId>` |
| Обёрнутый notebookKey ключом сервера | `ds1|key|notebook-server|<notebookId>` |
| Обёрнутый noteKey ключом блокнота | `ds1|key|note|<noteId>` |
| Кусок вложения | `ds1|att|<attachmentId>|<index>|<last: 0 или 1>` |
| Секретный ключ пары аккаунта мастер-ключом (§10) | `ds1|key|account-box|<userId>` |
| Ключ блокнота/заметки версии ≥ 2 (§10.3) | `ds1|key|notebook|<id>|<version>`, `ds1|key|note|<id>|<version>` |
| Звено цепочки: ключ версии `v−1` ключом версии `v` | `ds1|key|prev|<notebook или note>|<id>|<v>` |
| Ключ для участника (§10.2) | `ds1|key|member|<notebook или note>|<id>|<version>|<ownerUserId>|<memberUserId>` |

В JSON и URL конверт передаётся в base64url без padding.

## 4. Ключ восстановления

- 32 случайных байта, показываются пользователю один раз в виде **Crockford Base32** (52 символа), группами по 4 через дефис, с префиксом `DS1-`.
- `recoveryLoginKey = crypto_generichash(32, "ds1|recovery-login", key = recoveryKey)`; сервер хранит `Argon2id(recoveryLoginKey)`.
- **Замена ключа восстановления** (например, старый потерян или мог попасть к посторонним): клиент создаёт новый `recoveryKey`, считает новый `recoveryLoginKey`, оборачивает `masterKey` новым ключом (`ad = ds1|key|master|recovery|<userId>`) и отправляет `POST /v1/auth/recovery-key` с подтверждением текущим `loginKey`. Сервер атомарно заменяет `Argon2id(recoveryLoginKey)` и `wrappedMasterKeyRecovery`; старый ключ восстановления перестаёт работать. Новый ключ показывается пользователю один раз. Данные не перешифровываются.
- Восстановление: клиент доказывает знание ключа восстановления (`recoveryLoginKey`), получает `wrappedMasterKeyRecovery`, расшифровывает masterKey, задаёт новый пароль (новая соль, новый `loginKey`, новый `wrappedMasterKeyPassword`). Данные не перешифровываются.

## 5. Смена пароля

Перешифровывается только обёртка masterKey: новая соль → новые `loginKey` и `passwordKey` → новый `wrappedMasterKeyPassword`.

## 6. Вложения

Файл режется на куски по **1 MiB** открытого текста; каждый кусок — отдельный конверт (`ad` с индексом и признаком последнего). Это позволяет докачку и проверку целостности по кускам.

## 7. Шеринг по ссылке

`https://<web-host>/s/<shareId>#k=<base64url ключа>` — для заметки в ссылке `noteKey`, для блокнота — `notebookKey`. Часть после `#` браузер не отправляет на сервер.

## 8. Режим «для агентов» (R-10)

- `serverKey` — 32 байта из переменной окружения сервера `DS_KMS_KEY` (base64url), **не** хранится в базе.
- При переводе блокнота в режим «для агентов» клиент отправляет `notebookKey` по TLS на `PATCH /v1/notebooks/:id/mode`; сервер сам оборачивает его `serverKey` и хранит только обёртку. Обратный перевод — сервер удаляет обёртку.
- Сервер расшифровывает `notebookKey` только в момент обработки запроса агента с действительным токеном и правами на блокнот.
- Расшифрованные ключи заметок держатся в памяти сервера не дольше 10 минут (не больше 10 000 записей) и сбрасываются сразу при выходе блокнота из режима «для агентов», удалении блокнота и отзыве или сужении разрешения агента.

## 9. Тестовые векторы

`packages/test-vectors/crypto/`: KDF (пароль + соль → loginKey, passwordKey), конверты (ключ + nonce + ad + plaintext → bytes), Crockford Base32 ключа восстановления, куски вложения. Обязательны для Swift и TS: одинаковые входы → одинаковые байты. Векторы общего доступа (§10): `crypto/sharing.json` — пары ключей из seed, обёртка секретного ключа, ключ для участника в обе стороны, цепочка ключей, код безопасности.

## 10. Ключи аккаунтов и общий доступ (D-54)

Совместная работа по аккаунтам: владелец блокнота или заметки выдаёт другому аккаунту её ключ так, что сервер его не видит. Реализация TS — `packages/shared/src/crypto/sharing.ts`.

### 10.1. Пара ключей аккаунта

- У каждого аккаунта есть пара ключей **X25519** (`crypto_box_keypair`): 32 байта открытого ключа, 32 байта секретного.
- Секретный ключ хранится на сервере обёрнутым мастер-ключом: `ad = ds1|key|account-box|<userId>`. Открытый ключ сервер публикует (`api.md`, «Совместный доступ»).
- Пару создаёт клиент при регистрации, а у существующих аккаунтов — при первом входе новой версии (`PUT /v1/me/box-key`, один раз). Клиент, развернув секретный ключ, проверяет, что он соответствует опубликованному открытому (`crypto_scalarmult_base`); иначе — ошибка, ключи не используются.
- Смена пары ключей в этой версии не предусмотрена (при смене пароля и восстановлении меняется только обёртка мастер-ключа, пара остаётся прежней).

### 10.2. Ключ для участника

Владелец оборачивает ключ блокнота (или одной заметки) для участника так:

```
shared   = crypto_box_beforenm(memberPublicKey, ownerSecretKey)      // X25519 + HSalsa20, 32 байта
wrapKey  = crypto_generichash(32, message = "ds1|member-wrap", key = shared)
wrapped  = конверт §3 (wrapKey, ad = ds1|key|member|<kind>|<targetId>|<version>|<ownerUserId>|<memberUserId>, ключ)
```

`kind` — `notebook` или `note`, `version` — версия ключа (§10.3). Участник считает тот же `wrapKey` из своего секретного ключа и открытого ключа владельца.

**Почему так, а не `crypto_box_seal`:** запечатанный конверт не принимает `ad`, а здесь важно привязать обёртку к блокноту, версии ключа и обоим аккаунтам, чтобы сервер не мог подсунуть обёртку от другого блокнота или старую версию. Обычный `crypto_box` даёт `ad` только через свой формат. Схема «общий ключ двух аккаунтов + наш конверт» использует уже проверенный конверт и функции, которые есть и в `libsodium-wrappers-sumo`, и в `swift-sodium` (`box.beforenm`). Кроме того, участник проверяет автора обёртки: подделать её может только владелец секретного ключа владельца. Сервер раздаёт открытые ключи, поэтому подменить ключ целиком он может; от этого защищает код безопасности (§10.5).

### 10.3. Версии ключей и смена ключа

- У ключа блокнота и ключа заметки есть **версия**, начиная с 1. Обёртки версии 1 используют прежние `ad` (`ds1|key|notebook|<id>`, `ds1|key|note|<id>`); версии ≥ 2 — с суффиксом: `ds1|key|notebook|<id>|<version>`, `ds1|key|note|<id>|<version>`. Так сервер не может подменить новую обёртку старой.
- **Когда меняется:** владелец убрал участника, участник вышел сам или удалил свой аккаунт. Сервер в этот момент ставит ресурсу `keyRotationPending`; ключ меняет **клиент владельца** — сразу, если удалял он, иначе при следующем запуске. До смены ключа удалённый уже не получает от сервера ничего — сервер закрывает ему доступ сразу.
- **Порядок смены (блокнот):**
  1. новый `notebookKey` версии `v+1`; обёртки нового ключа: для владельца — мастер-ключом, для каждого оставшегося участника со статусом `active` — §10.2 (ждущие ключа получат его новой версии позже, как обычно); звено цепочки — старый ключ, обёрнутый новым (`ad = ds1|key|prev|notebook|<id>|<v+1>`); для режима «для агентов» — сам новый ключ (сервер оборачивает его своим, §8). Всё это — **один запрос** `POST /v1/members/notebook/:id/rotate` (`api.md`), который сервер выполняет одной транзакцией и только если `version` = текущая + 1 (два одновременных запроса не пройдут оба);
  2. **каждая заметка** блокнота получает новый `noteKey` версии `+1`; клиент пишет в индекс блокнота (обычным `push`, уже новым ключом блокнота) `NoteMeta.wrappedKey` — новый ключ под новым ключом блокнота — и `NoteMeta.keyVersion`, `NoteMeta.keyChain` (звено `ad = ds1|key|prev|note|<noteId>|<версия>`). Иначе удалённый, знающий старые ключи заметок, смог бы прочесть новые правки, если бы сервер их ему отдал;
  3. когда все заметки обработаны и индекс подтверждён (`ack`), клиент вызывает `POST /v1/members/notebook/:id/rotate/done` — сервер снимает `keyRotationPending`. Если клиент прервался между шагами, при следующем запуске он видит `keyRotationPending` и доделывает шаг 2 для заметок со старой версией ключа.
  **Пока идёт шаг 2** (обычно секунды, при обрыве — до следующего запуска владельца): заметки, ещё не получившие новый ключ, остаются на прежнем `noteKey` — участники читают и правят их как раньше (индекс и цепочку они расшифровывают новым ключом блокнота), а правки в них шифруются прежним ключом. Удалённый участник их не получает: сервер закрыл ему доступ ещё до шага 1. Заметки с новым ключом сразу шифруются им. Читатель ничего особого не видит; в интерфейсе владельца — ненавязчивое «Обновляем ключи доступа…», пока флаг не снят.
- Новые правки шифруются новым ключом. **Старые обновления и версии истории не перешифровываются:** клиент, у которого ключ версии `v`, разворачивает цепочку назад и пробует ключи по очереди, от нового к старому (у конверта нет номера ключа; неверный ключ просто не проходит проверку тега). Цепочка нужна и новому участнику, чтобы прочесть историю до своего прихода.
- Удалённый сохраняет всё, что уже успел расшифровать, — это честное ограничение сквозного шифрования.
- Одна заметка, расшаренная отдельно, меняет ключ одним запросом `POST /v1/members/note/:id/rotate` (новый `noteKey`, обёртки, звено цепочки); он же снимает `keyRotationPending`. Затем клиент владельца записывает новые `wrappedKey`, `keyVersion`, `keyChain` в `NoteMeta` индекса своего блокнота обычным `push`. Если он прервался до этого, при следующем запуске берёт ключ из `GET /v1/members/note/:id/key` и дописывает `NoteMeta`.
- **Ссылки для гостей** (§7) содержат ключ, поэтому после смены ключа новых правок по старой ссылке не видно. Клиент владельца после смены ключа сам **пересоздаёт** ссылки этого ресурса: отзывает старые (`DELETE /v1/shares/:id`), создаёт новые с теми же правами и сроком и новым ключом в `#k=` и показывает «Ссылки обновлены — отправьте новые» (решение владельца продукта, 2026-10-27, D-54).

### 10.4. Участник создаёт заметку

Участник с правом «Может редактировать» создаёт заметки в общем блокноте как обычно: новый `noteKey` версии 1, обёртка текущим ключом блокнота в `NoteMeta`. Права на запись проверяет сервер (`sync-protocol.md` §6, `api.md` «Совместный доступ»): окончательно удалить или вынести заметку из общего блокнота может только владелец.

### 10.5. Код безопасности (необязательно, в интерфейсе пока не показывается)

```
msg  = UTF-8 "<userIdA>|<userIdB>|" ‖ publicKeyA ‖ publicKeyB      // A — меньший userId (сравнение строк)
h    = crypto_generichash(30, msg, key = "ds1|safety-code")
код  = 6 групп по 5 цифр: группа i = (h[5i..5i+4] как беззнаковое big-endian) mod 100000, с ведущими нулями, через пробел
```

Одинаков у обоих участников; меняется, если сервер подменил чей-то открытый ключ. Сверка кодов — по желанию пользователей (D-54: обязательной сверки нет).
