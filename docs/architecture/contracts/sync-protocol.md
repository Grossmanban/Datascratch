# Контракт: протокол синхронизации (версии 1–2)

Связано: D-25 (без Redis), D-31 (Yjs), `spec/10-sync.md`. Типы TS: `packages/shared/src/contracts/sync.ts`.

## 1. Принципы

- Единица синхронизации — документ Yjs (`account`, `notebook`, `note`).
- Клиент отправляет **зашифрованные** обновления Yjs; сервер присваивает им порядковый номер `seq` (строго возрастающий в пределах документа), хранит и рассылает подписчикам. Сервер их не сливает и (для приватных блокнотов) не может прочитать.
- Клиент хранит у себя `lastSeq` по каждому документу и при подключении догоняет недостающее.
- Офлайн: обновления копятся в локальной очереди и отправляются при подключении; подтверждение — `ack`. Неподтверждённое не удаляется из очереди.
- Клиенту не обязательно держать документ в памяти: подписанный документ можно хранить только как сохранённое состояние (склеивая полученные обновления через `Y.mergeUpdates`) и поднимать `Y.Doc` при открытии. Протокол от этого не меняется (уточнение потока core, 2026-10-25; TS — режим «stored» в `SyncClient`).

## 2. Транспорт

`wss://<host>/v1/sync` (локально — `ws://`). Текстовые кадры WebSocket, каждое сообщение — JSON-объект с полем `type`. Двоичные данные — **base64url без padding**. Пинг — стандартные ping/pong WebSocket каждые 25 с.

**Версии протокола** (2026-11-08, по поручению координатора). Клиент пишет в `hello.protocol` самую новую версию, которую знает; сервер отвечает в `welcome.protocol` версией, на которой будет говорить: не выше версии клиента и не выше своей. Версия 2 добавляет сообщение `account_changed` (§4); сервер шлёт его только соединениям с версией ≥ 2. Сервер, не знающий версию клиента, отвечает `error protocol_mismatch`; клиент тогда один раз повторяет подключение с версией на 1 ниже (до 1) — это не ошибка для пользователя. Типы TS: `SYNC_PROTOCOL_MIN = 1`, `SYNC_PROTOCOL_LATEST = 2`.

**Правило совместимости вперёд.** Клиент молча пропускает сообщение сервера с неизвестным `type`: так новый сервер не ломает старых клиентов. Ошибкой («некорректное сообщение сервера») остаются только кадр, который не разбирается как JSON, кадр без строкового `type` и сообщение известного типа, не прошедшее проверку схемы.

## 3. Сообщения клиента

| `type` | Поля | Смысл |
| --- | --- | --- |
| `hello` | `protocol: 1 \| 2` (самая новая версия клиента, §2), `auth: { kind: "user", accessToken } \| { kind: "guest", shareId, guestToken }`, `deviceId`, `client: { platform: "ios"\|"web", version }` | Первое сообщение. До `welcome` другие не принимаются |
| `subscribe` | `docs: [{ docId, since }]` (1–1000 документов, без повторов `docId`; больше — несколькими сообщениями) | Подписаться и получить всё после `since` (0 — с начала) |
| `unsubscribe` | `docIds: string[]` | |
| `push` | `docId`, `clientMsgId`, `payload` | Отправить зашифрованное обновление |
| `snapshot` | `docId`, `clientMsgId`, `baseSeq`, `payload` | Загрузить зашифрованный снимок состояния, включающий все обновления до `baseSeq` |
| `awareness` | `docId`, `payload` | Курсоры/присутствие (зашифровано, не хранится, только рассылается) |

## 4. Сообщения сервера

| `type` | Поля | Смысл |
| --- | --- | --- |
| `welcome` | `userId \| null`, `serverTime`, `protocol: 1 \| 2` (версия этого соединения) | Аутентификация успешна |
| `updates` | `docId`, `snapshot: { seq, payload } \| null`, `items: [{ seq, payload, deviceId, author? }]`, `upToDate: boolean` | Ответ на `subscribe` (может прийти несколькими частями; последняя — `upToDate: true`) |
| `update` | `docId`, `seq`, `payload`, `deviceId`, `author?` | Живое обновление от другого устройства |
| `ack` | `docId`, `clientMsgId`, `seq` | Обновление/снимок принят и сохранён (для снимка `seq` = его `baseSeq`) |
| `awareness` | `docId`, `payload`, `deviceId` | |
| `error` | `code`, `message`, `ref?` | См. коды ниже. Для ошибок `push`/`snapshot` `ref` = их `clientMsgId`, иначе — `docId` при наличии |
| `account_changed` | `what: string[]` (до 8 значений из `invitations`, `spaces`, `members`, `keys`, `notebooks`, `voice` (доступ к голосу и квота, D-65); неизвестные значения клиент отбрасывает) | **Версия 2.** На сервере изменилось общее состояние аккаунта: приглашения, участники, обёртки ключей, блокноты пространства, смена ключа. Клиент сразу перечитывает затронутое по REST (`api.md`), а не ждёт опроса раз в 120 с. Ничего не несёт само: только подсказка, что перечитать |

**Автор обновления (D-54).** `author` — `Author` из `api.md`: `{ kind: "user", userId }`, `{ kind: "guest", shareId }` (непрозрачный id гостя, не id ссылки — см. `api.md`) или `{ kind: "agent", tokenId }`. Его ставит **сервер** по тому, кто прислал обновление (аутентификация соединения или токен агента), клиент автора не сообщает. Новый сервер присылает `author` всегда; поле необязательно в схеме, чтобы клиенты понимали и старый сервер. Курсоры соавторов (awareness) подписываются именами из открытого содержимого awareness, сервер их не проверяет.

**Порядок (обязательно для сервера):** назначение `seq` и рассылка внутри одного документа сериализованы — подписчики получают обновления строго в порядке `seq`, и `ack` отправителю уходит не раньше, чем обновление записано. Клиент хранит `lastSeq = max(seq)` из `updates`/`update`/`ack`; при нарушении порядка обновление могло бы потеряться при обрыве. «Дыры» в `seq` допустимы.

**Клиент** подписывается на документ (`subscribe`) **до** первого `push` в него — иначе `lastSeq = max(ack)` может перескочить чужие обновления, пришедшие раньше (уточнение потока server). Идентификатор устройства гостя — `guest:<22 символа хэша>` (укладывается в лимит 64 символа).

Сервер не присылает клиенту его собственные обновления (кроме как в `updates` при догоняющей подписке с другого устройства).

## 5. Снимки и уплотнение (R-05)

- Клиент, у которого по документу накопилось > 500 обновлений после последнего снимка (или > 1 MiB), собирает снимок (`Y.encodeStateAsUpdate`), шифрует и шлёт `snapshot` с `baseSeq` = последний применённый `seq`. Снимки — это ещё и версии истории (`spec/06`), поэтому клиент шлёт снимок также (решение владельца, 2026-11-09):
  - при уходе из документа, его закрытии или уходе приложения в фон — если с последнего снимка сделана хотя бы 1 правка и прошло ≥ 2 минут;
  - каждые 10 минут, пока документ правят;
  - **до** применения предложения («Оформить», правки агента `agentEdit`) и до вставки текста голосом — чтобы к прежнему виду можно было вернуться.

  Пороги 500 обновлений / 1 MiB остаются.
- Сервер хранит снимок и может удалить обновления с `seq ≤ baseSeq`, **кроме** тех, что нужны истории версий (политика хранения истории — `spec/10-sync.md`, детали — в потоке сервера).
- При `subscribe` с `since` < `seq` последнего снимка сервер присылает последний снимок + всё после него (всегда, а не только после уплотнения: меньше обновлений к применению, и клиент, пропустивший испорченное обновление, восстанавливается по более позднему снимку). Уточнение 2026-10-26 (предложение потока core, принято координатором).
- **Большая правка — обычным `push` (решение координатора, 2026-11-11).** Обновление может быть до 16 MiB (§7), у большой правки свой `seq`: догоняющая подписка и рассылка работают как для любой правки. Клиенты, которые ещё держат лимит 2 MiB, шлют большую правку снимком — для них остаётся рассылка ниже.
- **Снимок — подписанным устройствам сразу (2026-11-11).** Правку больше своего лимита обновления клиент шлёт не `push`, а `snapshot` (до 16 MiB, в нём вся заметка вместе с правкой). Принятый снимок сервер сразу пересылает другим соединениям, подписанным на документ, — тем же кадром `updates`: `{ docId, snapshot: { seq: baseSeq, payload }, items: [], upToDate: false }` (отправителю — нет). `upToDate: false` — чтобы не спутать с ответом на `subscribe`: документ «догнан» только по последнему кадру этого ответа (с `true`), а разосланный снимок приходит уже живой подписке. Кадр уже известен клиентам, менять их не нужно: клиент применяет снимок как обычно и ставит `lastSeq = max(lastSeq, baseSeq)`; снимок содержит все обновления до `baseSeq`, поэтому идёт вне порядка `seq`. Соединение, которое ещё догоняет, получает только последний такой снимок — после своей догоняющей подписки. Пересылаются все снимки, в том числе снимки версий (они редки: уход из заметки, раз в 10 минут). **Ограничение (поэтому большие правки — `push`):** устройство, которое было не в сети и вернётся с `since ≥ baseSeq`, правку из снимка при подписке не получит (снимок шлётся только при `since` < его `seq`), а второй снимок с тем же `baseSeq` сервер не сохраняет.
- Клиент, который не может расшифровать или применить элемент, пропускает его (курсор двигается дальше), сообщает хосту `{ docId, seq, deviceId, причина }` и может один раз переподписаться с `since: 0`, чтобы получить последний снимок.

## 6. Права

- `user`: доступ к документам своего аккаунта; документы блокнота регистрируются через REST (`api.md`, `POST /v1/docs`) до первого `push`.
- `guest`: только документы, входящие в шеринг (`api.md`, `/v1/shares`); `push` — только при праве `edit`.
- Участник общего блокнота или заметки (D-54, `api.md` «Совместный доступ»): `user`-соединение получает и документы ресурсов из `/v1/shared-with-me`. Роль `viewer` — только чтение: `push` и `snapshot` отклоняются `error forbidden` с `ref` = `clientMsgId` (клиент удаляет элемент из очереди и сообщает приложению), `awareness` принимается. Роль `editor` пишет как владелец, в том числе регистрирует новые заметки блокнота (`POST /v1/docs`). Когда участника убрали или он вышел, сервер сразу присылает подписанным документам `error doc_not_found` с `ref` = `docId` и больше их не отдаёт.
- Участник общего пространства (D-62, `api.md` «Общие пространства»): то же, что участник общего блокнота, для документа пространства (`kind = space`) и всех блокнотов и заметок пространства, включая созданные позже; новые документы пространства доходят до открытых соединений участников сразу. `viewer` не пишет и в документ пространства.
- **`account_changed` (D-62, 2026-11-08).** Когда сервер шлёт (§4; только соединениям версии ≥ 2): приглашения (созданы, приняты, отклонены, отозваны — приглашённому и приглашающему), участники ресурса (добавлен, роль, убран или вышел), выданные и сменённые ключи (пространства, блокнота, заметки), блокноты общего пространства (созданы, перенесены, удалены — всем участникам) и смена ключа пространства. Какой REST-вызов что шлёт — `api.md`, «Уведомления об изменениях аккаунта». Кадр уходит **всем соединениям** затронутых аккаунтов, в том числе устройству, которое само сделало изменение, и только после фиксации изменения. Изменения в пределах 250 мс на соединение склеиваются в один кадр; сервер шлёт непустой `what` без повторов. Клиент перечитывает названное и подписывает появившиеся документы **в том же соединении**: отказ `doc_not_found` сервер не запоминает, повторный `subscribe` после выдачи доступа проходит. Проверка прав открытых подписок (выше) работает, как раньше, и для соединений версии 1.
- Агенты по WebSocket не подключаются — они работают через MCP/REST (сервер сам применяет их правки как обычные обновления).

## 7. Коды ошибок

У `error` с кодом `rate_limited` может быть необязательное поле `retryAfterMs` — клиент не повторяет отправку раньше (аудит 2026-10-27). При превышении частоты сообщений сервер соединение **не** закрывает (клиент приостанавливает отправку и затем повторяет неподтверждённое); при превышении числа соединений (10 на аккаунт, 30 на IP) — `rate_limited` и закрытие с кодом 1013, клиент переподключается не раньше `retryAfterMs`. До `hello` кадр не больше 64 КБ (иначе закрытие 1009), некорректное сообщение до `hello` — закрытие 4400.

`bad_request` (некорректное сообщение), `unauthorized`, `device_revoked` (с `reason`, закрытие 4410 — см. ниже), `forbidden`, `doc_not_found`, `payload_too_large` (лимит обновления 16 MiB — с 2026-11-11, до этого 2 MiB; снимка 16 MiB (уточнение потока server, 2026-10-27) — считаются **декодированные** байты, не base64), `rate_limited`, `protocol_mismatch`, `internal`.

**Отзыв устройства (2026-10-27, поручение координатора; коды согласованы с потоком core).** Если устройство отозвано — во время работы соединения или к моменту `hello` (токен отозванного устройства), — сервер присылает `error` с `code: "device_revoked"` и полем `reason` и закрывает соединение кодом **4410**, повторяя `reason` в причине закрытия. Значения `reason` — те же, что в REST (`api.md`, «Аутентификация»): `user`, `password_change`, `recovery`, `token_reuse`, `account_deleted`. На `hello` с токеном отозванного устройства `welcome` не приходит: сразу `error device_revoked`, затем закрытие 4410. Для уже открытого соединения — в любой момент после `welcome`. Кадр `error` всегда идёт перед закрытием. Если клиент получил закрытие 4410 без него (кадр потерян), причина берётся из reason закрытия, а если её нет или она неизвестна — `user`. Клиент по `device_revoked` / 4410 **стирает локальные данные**, не переподключается и не отправляет очередь. Старые клиенты, не знающие код 4410, переподключаются с задержкой и снова получают отказ, а при обновлении токена — 401: им нужно войти снова, данные не стираются. Код 4401 (`unauthorized`) этого не означает: это неверный или истёкший токен, отозванная или истёкшая ссылка гостя.
