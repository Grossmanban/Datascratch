# D-46. Ускорение проверок iOS: без повторов на main и быстрый набор перед сборкой

- **Статус:** РЕШЕНО (пользователь, 2026-10-26)
- **Дата:** 2026-10-26
- **Связано:** `docs/development.md` («Проверки iOS и сборки TestFlight»), D-39 (правила сессий-исполнителей)

## Контекст

Сборка TestFlight ждала проверки iOS ~40 минут, затем ~30 минут сборки и до 30 минут обработки Apple. Пользователь разозлился на сроки. Две причины, которые можно убрать:

1. После слияния проверенной ветки в `main` те же проверки iOS запускались ещё раз и занимали немногочисленные машины macOS — следующий кандидат в сборку стоял в очереди ~20 минут.
2. Сборка ждала все UI-тесты (13–19 минут), хотя критичные сценарии проверяются за несколько минут.

## Решение

1. **Без повторов на `main`.** В `ios-app`, `ios-editor`, `ios-core`, `design` первым идёт лёгкий шаг `gate` (Linux): при пуше в `main` он ищет успешный прогон того же workflow на коммите с **теми же файлами** в отслеживаемых путях (`.github/scripts/already-tested.sh`). Нашёл — задачи macOS пропускаются. Для `ios-editor` прогон считается успешным, если упал только известный шаг демо-набора текста. В ветках и PR проверки идут как раньше.
2. **Быстрый набор — ворота сборки.** UI-тесты `ios-app` разделены на два шага: «UI tests (smoke — release gate)» (запуск, редактор, палитра пера, скрытие клавиатуры, колонки iPad, «устройство отключено», русский интерфейс — список в `SMOKE_UI_TESTS`) и «UI tests (full)» сразу за ним. Координатор запускает сборку TestFlight, как только быстрый набор зелёный на iPhone и iPad (`tools/ci/wait-release-gate.sh <run>`), не дожидаясь полного. Если полный набор потом падает — исправление идёт в следующую сборку, о падении сообщается пользователю.

3. **Параллельные части (поправка 2026-11-08, пользователь: «почему одна проверка 45 минут» → «сделай разбиение на части»).** Прогон `ios-app` теперь из трёх задач на каждое устройство (iPhone, iPad):
   - **Build** — одна машина собирает приложение и тесты (`build-for-testing`), проверяет каталог строк и русский язык в сборке и отдаёт собранное следующим задачам (артефакт `products-<устройство>`, хранится 1 день);
   - **Unit & smoke** — модульные тесты и быстрый набор (ворота сборки, как в п. 2);
   - **UI tests (N/3)** — остальные UI-тесты, разложенные на `UI_SHARDS` = 3 части (`apps/ios/scripts/ui-test-shard.py`: все тест-методы из исходников, без быстрого набора, по кругу в постоянном порядке).
   Unit & smoke и три части идут одновременно на разных машинах. Ни один тест не пропадает: шаг «Check the UI shards cover every test» в Build сверяет число объявленных `func test…` с найденными и проверяет, что части вместе с быстрым набором дают весь набор ровно по одному разу, — иначе прогон красный. `tools/ci/wait-release-gate.sh` смотрит задачи «Unit & smoke» (и старые «Build & test» для прошлых прогонов).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Без повторов + быстрый набор** | −20 мин очереди, −10–15 мин на сборку, бесплатно | Сборка может уйти с ошибкой, которую ловит только полный набор |
| Платные быстрые машины GitHub | Быстрее всё | Деньги; пользователь пока не выбрал |
| Ничего не менять | Максимум проверок до сборки | Медленно |
| Части на разных машинах (поправка 2026-11-08) | Полный набор ~15–20 мин вместо ~45, бесплатно (открытый репозиторий) | Больше машин macOS одновременно — при очереди части ждут; сборка выкладывается артефактом (~1–2 мин) |
