# 6. Модель данных и сервер

Решения: D-01 (база, не файлы), D-21 (стек), D-25 (без Redis), D-26 (хранение файлов), D-30 (PostgreSQL), D-31 (Yjs).

## Модель данных (общий обзор; детали — `architecture/data-model.md`)

- **Текст** — дерево блоков в CRDT (**Yjs**; на iOS — Yrs): правки с разных устройств, от гостей и от агента сливаются без конфликтов.
- **Слой рукописи** — векторные штрихи (точки, нажим, наклон, время, инструмент, цвет, толщина) с якорями. Типы якорей: диапазон текста, абзац (поля), блок рисования, картинка.
- **Вложения** — отдельные зашифрованные файлы, загрузка по требованию, докачка.
- **Метаданные** — заголовок, теги, ссылки, даты, пространство, папка.
- Все форматы (документ, штрих, метаданные) **версионируются с первого дня** (R-03).

## Сервер

Отвечает за: аккаунты, хранение и ретрансляцию зашифрованных изменений, вложения, реальное время, API и MCP, рендер рукописи в PNG для агентов.

Состав (после решений D-25, D-26):

| Компонент | Что | Зачем |
| --- | --- | --- |
| Сервер приложения | Node.js + TypeScript (Fastify) | Синхронизация, реальное время, API, MCP |
| База данных | **PostgreSQL** (через Drizzle) | Аккаунты, блокноты, права, токены, зашифрованные обновления, снимки истории, журнал агентов; заодно очередь фоновых задач (pg-boss) |
| Хранилище файлов | **Папка на диске** по умолчанию; **внешнее S3-совместимое** — опционально, по настройке | Вложения (уже зашифрованы на клиенте) |

**Redis не используется** (D-25): сервер работает одним процессом, рассылка правок в реальном времени идёт в памяти процесса. Рассылка спрятана за отдельным интерфейсом, чтобы при необходимости масштабирования подключить PostgreSQL LISTEN/NOTIFY или Redis/Valkey, не трогая остальной код.

**MinIO не используется** (D-26): хранение файлов спрятано за интерфейсом с двумя реализациями — «диск» и «S3».

## Адрес сервера в клиентах (D-49)

- iOS/iPadOS: поле «Сервер» на экране входа и регистрации; человек вводит адрес сам (`https://`, проверка `GET /v1/health` до входа). Адрес хранится с аккаунтом; сменить сервер — выйти и войти на другом.
- **Наш сервер не показывается нигде** (пользователь, поправка D-49 от 2026-10-27: «это мой личный сервер»):
  - поле пустое, с нейтральной подсказкой «адрес вашего сервера, например notes.company.ru»;
  - адрес из сборки (`DS_SERVER_URL`) не подставляется и не появляется ни в подсказках, ни в ошибках, ни в «О приложении»;
  - адрес приходит только от человека, из ссылки-приглашения или из уже сохранённого входа на этом устройстве.
- **iOS (build 17):** поле «Сервер» над почтой; адрес можно ввести без схемы (`sync.example.org` → `https://sync.example.org`), `http://` — только для `localhost`; Return в поле или «Войти»/«Продолжить» проверяют сервер (`GET /v1/health`), и под полем появляется «имя · версия» (или причина отказа) — только потом уходит пароль. Выбранный сервер запоминается на устройстве и при следующем запуске подставляется сам; сменить его можно только без вошедшего аккаунта. В «Настройки → Аккаунт» строка «Сервер». Поле есть в любой сборке; без входа приложение работает только на устройстве.
- Ссылки шеринга и приглашений несут адрес сервера: по ссылке сервер уже выбран, человек входит или регистрируется и сразу получает общий доступ.
- Несколько серверов/аккаунтов одновременно — этап 6.
- Веб работает с сервером своего домена.

## Self-hosting

Весь сервер поднимается одной командой `docker compose up` (`infra/`): два контейнера — сервер и PostgreSQL. Ориентир по ресурсам: VPS на 2 ядра, 2–4 ГБ памяти; в простое комплект занимает ~300–400 МБ памяти.

## Резервные копии

Ежедневные резервные копии БД и файлов, хранятся **вне** этого VPS; восстановление проверяется (R-11).

## Реализация сервера (поток server, 2026-10-25)

Код — `apps/server`, развёртывание — `infra/` (`infra/README.md`). Таблицы — `architecture/data-model.md`. Ниже — правила, которых нет в контрактах и которые выбраны при реализации (статус **ПРЕДЛОЖЕНО**, пересматриваются через координатора).

### Вход и сессии (D-34, `contracts/crypto.md`)

- Сервер хранит `Argon2id(loginKey)` и `Argon2id(recoveryLoginKey)` (m = 19 МиБ, t = 2: ключи уже высокоэнтропийные, клиент сам делал тяжёлый Argon2id).
- `prelogin` для неизвестного email отдаёт детерминированную фальшивую соль (HMAC от секрета сервера) и параметры по умолчанию; вход и восстановление для неизвестного email тратят столько же времени, сколько для известного.
- Устройство = сессия. Access-токен (JWT, 15 мин) несёт `userId` и `deviceId`; отзыв устройства действует сразу (сервер проверяет устройство на каждом запросе и закрывает его WebSocket).
- Refresh-токен (30 дней) одноразовый: при обновлении выдаётся новый. Повторное предъявление уже использованного — признак кражи: устройство отзывается целиком. Исключение — повтор в течение 60 с (`REFRESH_REUSE_GRACE_SEC`), пока новый токен ещё не использован: сервер возвращает тот же новый токен. Так потерянный в нестабильной сети ответ не отключает устройство. Новый токен не хранится: он вычисляется из старого (HMAC на серверном ключе). Клиент должен обновлять токен последовательно, не из двух вкладок сразу.
- Ключ восстановления можно заменить (`POST /v1/auth/recovery-key`, с подтверждением паролем): старый перестаёт работать сразу, начатые с ним восстановления отменяются, устройства остаются в системе. Смена пароля, восстановление и замена ключа записываются в журнал безопасности (`GET /v1/me/security-events`).
- Смена пароля отзывает все **другие** устройства; восстановление по ключу восстановления — **все** (выдаётся новая сессия).
- `Session` дополнительно содержит `deviceId` (предложено координатору как дополнение контракта). В `signup` и `recovery/finish` принимается необязательное `deviceName`.

### Квоты и регистрация (аудит безопасности 2026-10-27)

- У каждого аккаунта есть квота хранения (`USER_STORAGE_QUOTA_BYTES`, по умолчанию 10 ГБ — подтверждено владельцем, D-53; 0 — без ограничения). В неё входят обновления, снимки и вложения (по заявленному размеру). Записи гостей и агентов считаются владельцу заметки. Счётчик `users.storage_bytes` ведут триггеры базы, так что учитывается любой путь записи. Сверх квоты — `payload_too_large` «storage quota exceeded». Для снимков запас 10 %, чтобы у аккаунта на пределе можно было уплотнить историю. Удаление заметок и уплотнение освобождают место.
- Регистрация: `DS_SIGNUP=open` (по умолчанию; владелец оставил регистрацию открытой — D-53), `closed` (только существующие аккаунты) или `invite` (нужен код из `DS_INVITE_CODES`, через запятую). Повтор регистрации того же аккаунта после потерянного ответа работает при любом режиме.
- Конфликт при регистрации (адрес, `userId` или `accountDocId` заняты) — всегда один и тот же ответ `409`. Узнать, что адрес занят, всё равно можно по самому отказу: без подтверждения адреса по почте это не устранить. Перебор адресов сдерживают лимиты частоты.

### Синхронизация (`contracts/sync-protocol.md`)

- `seq` выдаётся в транзакции под блокировкой строки документа — строго по возрастанию без пропусков. Подписчики получают живые обновления строго по порядку `seq`.
- Повторный `push` с тем же `clientMsgId` с того же устройства не создаёт дубль: приходит `ack` с прежним `seq`.
- Для пользователя `deviceId` в обновлениях — устройство из access-токена; для гостя — `guest:<22 символа хэша от shareId и deviceId из hello>` (контракт ограничивает deviceId 64 символами); для агента — `agent:<grantId>`.
- Некорректное сообщение → `error` с кодом `bad_request` (`ref` = `clientMsgId`, если он есть); `protocol_mismatch` — только неподдерживаемая версия протокола.
- Лимиты: обновление 2 МБ, снимок 16 МБ (было 50 МБ; снижено по аудиту безопасности 2026-10-27, предел в контракте `sync-protocol.md` должен обновить поток core), awareness 64 КБ, 100 сообщений/с на соединение (всплеск ×5; проверяется до разбора JSON; в отказе `rate_limited` поле `retryAfterMs` — через сколько сообщение снова примут); awareness — только по документам, на которые есть подписка.
- До успешного `hello` соединение принимает кадры не больше 64 КБ (больше — закрытие с кодом 1009); полный предел действует только после входа. Не больше 30 соединений с одного адреса и 10 на аккаунт (гости — на ссылку): сверх этого — `error rate_limited` с `retryAfterMs: 30000` и закрытие с кодом 1013 «повторите позже» (`SYNC_MAX_CONN_PER_IP`, `SYNC_MAX_CONN_PER_USER`). Если необработанных сообщений накопилось 32, сервер перестаёт читать сокет, пока очередь не уменьшится до 8.
- Удаление документа/блокнота присылает подписчикам `error doc_not_found` с `ref = docId`.
- `subscribe`: повторы одного документа схлопываются (считается последний `since`); повторы и больше 1000 документов в одном сообщении (`MAX_SUBSCRIBE_DOCS`, контракт) — `bad_request`; клиенты делят подписку на части. Пакетная выдача ограничена и по объёму: не больше 8 МБ на пакет. Документ, у которого после снимка накопилось больше 1 МБ (или сам снимок больше 1 МБ), выдаётся постранично (аудит безопасности 2026-10-27).

### Снимки, уплотнение и история версий (R-05)

- Снимки делает клиент (`snapshot`, > 500 обновлений или > 1 МБ), а также **при уходе из документа, если в нём сделано ≥ 30 правок** с последнего снимка — иначе версии истории получаются слишком редкими (ПРЕДЛОЖЕНО потоком web-app, 2026-10-25). Для блокнотов «для агентов» сервер делает снимки и сам, после правок агентов (ключ у него есть).
- **Версии истории = снимки.** `GET /v1/docs/:id/versions` — список снимков.
- Обновления, вошедшие в последний снимок, хранятся ещё **7 дней** (запас на время, пока снимок новый), потом удаляются. Догоняющему устройству они не нужны: оно получает снимок.
- Снимки: последний — всегда; все — за **7 дней**; затем один в день до **30 дней**, один в неделю до **года**, дальше — один в месяц. Сроки настраиваются переменными `HISTORY_*`.
- Первая синхронизация: подписка на много документов обрабатывается пакетно — по 200 документов за запрос, если у документа после `since` (или после последнего снимка) ≤ 100 обновлений; остальные идут по одному. Выдача притормаживает, пока в сокете больше 4 МБ непрочитанного (клиент не захлёбывается и не отключается). Замер (`pnpm --filter @datascratch/server bench`, один `subscribe` на 10 000 заметок, у каждой снимок ~3 КБ + обновление, локальный PostgreSQL): **~1,2 с** на стороне сервера (без снимков — ~0,9 с) при цели spec/11 «до минуты».
- При `subscribe` с `since` меньше `seq` последнего снимка сервер **всегда** шлёт этот снимок + обновления после него — даже если промежуточные обновления ещё хранятся (sync-protocol §5, изменение контракта 2026-10-26). Так устройство, которое не может прочитать часть обновлений (например, зашифрованных не тем ключом из-за ошибки клиента), восстанавливается по более позднему исправному снимку. Клиенты снимки уже применяют — совместимость не нарушена.

### Шеринг и гости (D-13, D-37)

- Шеринг блокнота даёт доступ к индексу блокнота и **всем** его заметкам, включая созданные позже.
- Гостевой токен живёт столько же, сколько ссылка; отзыв ссылки сразу отключает гостей, а в момент истечения срока ссылки сервер закрывает и уже открытые соединения гостей (`error unauthorized «share expired»`, код 4401). Гостевым токеном можно читать и (при праве `edit`) загружать вложения заметок шеринга; удалять — нельзя.
- Удаление заметки или блокнота отзывает его ссылки.

### Агенты (D-30)

- Агентский слой — пакет `@datascratch/agents` (поток agents), сервер даёт ему хранилище грантов/OAuth/журнала, расшифровку документов и вход пользователя (`apps/server/README.md`, «Агенты»).
- Каждый запрос агента к данным выполняется в транзакции под ролью PostgreSQL `ds_agent` с Row-Level Security по гранту: видны только его блокноты в режиме «для агентов», запись — только при `read_write`; отозванный или истёкший грант не видит ничего. Даже ошибочный запрос в коде не прочитает и не запишет чужой блокнот. Ключ блокнота расшифровывается только внутри такого запроса.
- Если блокнот переведён в приватный режим, агенты теряют к нему доступ сразу; удалённый блокнот убирается из грантов.
- Картинку-вложение для агента сервер расшифровывает только до 20 МБ (`AGENT_IMAGE_MAX_BYTES`). Доступ проверяется внутри транзакции под `ds_agent`, а чтение и расшифровка идут уже после неё и не держат соединение из пула (аудит безопасности 2026-10-27). Ограничение по пикселям — на стороне отрисовки (поток agents).
- Экран согласия OAuth открывается в браузере: веб-приложение ставит cookie сессии через `POST /v1/auth/web-session`.

### Фоновые задачи (pg-boss)

`doc-compact` (после нового снимка), `cleanup` (ежечасно: файлы удалённых вложений, брошенные незавершённые загрузки старше 7 дней, просроченные токены, отозванные устройства старше 30 дней), `history-sweep` (ежедневно: политика хранения истории по всем документам).

### Наблюдаемость

`GET /metrics` (формат Prometheus) включается переменной `METRICS_TOKEN` и требует `Authorization: Bearer <METRICS_TOKEN>`: HTTP-запросы, сообщения и ошибки синхронизации, сохранённые обновления (пользователь/гость/агент), открытые соединения, пул PostgreSQL, память и время работы. Без токена маршрута нет.

Журналы не содержат данных пользователей. Ошибки записываются по белому списку полей: параметры запросов к базе (адреса, хэши, шифртекст) и поле PostgreSQL `detail` отбрасываются — и из самого сообщения, и из стека; сообщения укорачиваются (аудит безопасности 2026-10-27).

### Адрес клиента и лимиты частоты (аудит безопасности 2026-10-27)

- `X-Forwarded-For` принимается только от прокси в частных сетях (`TRUST_PROXY`, по умолчанию `loopback,linklocal,uniquelocal`). Адрес клиента — самая правая запись, добавленная не доверенным узлом. Подставить свой адрес, дописав заголовок, клиент не может. Фрагмент для nginx передаёт `X-Forwarded-For $remote_addr`, без присланного клиентом.
- Кроме лимитов на адрес, у входа, регистрации, `prelogin` и восстановления есть лимит на адрес почты: 10 попыток в минуту на каждый вид запроса. Он действует, даже если запросы идут с разных адресов. Превышение лимита — `429 rate_limited` (раньше из-за ошибки в обработчике приходил `500`).
- До успешного `hello` любое некорректное сообщение сразу закрывает соединение (код 4400).
- Загрузка части вложения, которое удалили во время записи файла, отдаёт `404`, а записанный файл уходит на удаление (`storage_trash`).

### Перенос заметки между блокнотами

`PATCH /v1/docs/:id { notebookId }` меняет блокнот документа заметки; история, вложения и ключ заметки не меняются (ключ клиент переобёртывает ключом нового блокнота в индексе — `contracts/api.md`). Гости шеринга старого блокнота теряют заметку сразу, шеринг самой заметки остаётся; доступ агентов пересчитывается Row-Level Security по новому блокноту.

### Картинки по ссылке (D-52)

`POST /v1/fetch-image { url }` скачивает картинку для веба (у веба строгая политика безопасности, и сам он чужие сайты не открывает). Защита от обращений сервера туда, куда нельзя (SSRF):
- только `http`/`https`, порты 80/443, без логина и пароля в адресе;
- имя сайта разрешается в IP заранее. Если **хоть один** из адресов частный, локальный, служебный или зарезервированный, запрос отклоняется. Для IPv6 разрешены только глобальные адреса `2000::/3` без служебных блоков, поэтому формы со встроенным IPv4 (`::ffff:…`, NAT64, 6to4) тоже отклоняются. Хитрые записи IP (`2130706433`, `0177.0.0.1`) приводятся к обычному виду и проверяются;
- соединение идёт на уже проверенный IP: DNS не может подменить его между проверкой и запросом. Имя сайта используется только для заголовка `Host` и проверки HTTPS-сертификата;
- не больше 3 переадресаций, каждая проверяется заново;
- без cookies, авторизации и `Referer`, нейтральный `User-Agent`;
- не больше 20 МБ (обрыв при превышении, даже без `Content-Length`), 15 с на всё;
- принимаются только `Content-Type: image/*` с подтверждённой сигнатурой файла (PNG, JPEG, GIF, WebP, HEIC, AVIF). SVG не принимается. В ответе `Content-Type` берётся по сигнатуре;
- 60 запросов в минуту на аккаунт; одновременно не больше 2 скачиваний на аккаунт и не больше 4 на сервер (иначе `429`). Переменные `FETCH_IMAGE_PER_MINUTE`, `FETCH_IMAGE_MAX_BYTES`, `FETCH_IMAGE_TIMEOUT_MS`, `FETCH_IMAGE_CONCURRENCY`, `FETCH_IMAGE_CONCURRENCY_PER_USER`;
- адрес не пишется в журнал: только итог (`ok` или код ошибки) и длительность, плюс счётчик `ds_fetch_image_total{result}` в `/metrics`. Проверка после выкладки (`smoke.mjs`) заводит временный аккаунт, убеждается, что частные адреса отклоняются, и удаляет аккаунт.

### Автоматическое развёртывание (`infra/DEPLOY.md`)

Workflow `deploy` (вручную или при изменениях в `main`) собирает образы сервера и веба (веб-приложение + Caddy) в GHCR и выкладывает их на VPS пользователя по SSH (секреты `DEPLOY_HOST`, `DEPLOY_SSH_KEY`). Подготовка сервера идемпотентна: Docker, брандмауэр 22/80/443, автообновления, ночные копии; секреты сервера (`.env`) создаются один раз на самом сервере и никуда не передаются. Выкладка: миграции → `docker compose up` → проверка по HTTPS (API, веб, WebSocket, `/metrics` закрыт); если новая версия не поднялась или не прошла проверку — возврат на предыдущую. Веб, API (`/v1`), синхронизация и MCP — на одном домене; без своего домена адрес `<ip-с-дефисами>.sslip.io` с сертификатом Let's Encrypt. Сервер не обращается к Docker Hub (из России бывает недоступен): Docker ставится из репозитория Ubuntu, все образы, включая PostgreSQL, лежат в GHCR; нужные серверу внешние адреса перечислены в `infra/DEPLOY.md`. Память рассчитана на VPS 2 ядра / 4 ГБ: PostgreSQL — 1 ГБ (`shared_buffers` 256 МБ), сервер — 1 ГБ, Caddy — 256 МБ. Сценарий проверяется в CI на имитации VPS (Ubuntu 24.04 + sshd в контейнере).

**Сервер, где уже работают другие программы.** Перед выкладкой — режим разведки (`inspect`, только чтение, без предохранителя `DEPLOY_ENABLED`): система, память, диск, порты, Docker и его контейнеры, веб-серверы и их сайты, брандмауэр, автообновления — без секретов. Выкладка (только при `DEPLOY_ENABLED=true`) ничего чужого не меняет: использует уже установленный Docker, не трогает включённый `ufw` и автообновления, не включает брандмауэр на общем сервере, живёт в своём compose-проекте `datascratch` без «очисток». Рядом с Sinhron Datascratch встраивается в его Caddy: свой файл сайта в `/etc/sinhron/caddy-sites/`, общая docker-сеть `edge`, `caddy validate` перед перезагрузкой и удаление своего файла при ошибке; если Sinhron ещё не умеет принимать соседей — понятная ошибка, Sinhron Datascratch не обновляет. Если порты 80/443 заняты другим веб-сервером, Datascratch слушает только `127.0.0.1:8480`, а HTTPS остаётся за ним: готовые фрагменты для nginx/Caddy/Traefik, по желанию (`DS_NGINX_AUTO=true`) — автоматическое добавление сайта в nginx с бэкапом, `nginx -t` и возвратом при ошибке. На общем сервере лимиты памяти меньше (PostgreSQL 512 МБ, сервер 512 МБ, веб 128 МБ). Выбор режима — автоматически по разведке или переменной `DEPLOY_MODE` (`standalone` | `behind-proxy`).

### Корзина

Содержимое корзины (`trashedAt`) зашифровано в индексе блокнота, сервер его не видит. Через 30 дней клиент вызывает `DELETE /v1/docs/:id`; сервер удаляет документ, его историю и вложения сразу.
