# Как развернуть сервер Datascratch на своём VPS без компьютера (GitHub Actions)

Сервер и веб-приложение собираются в GitHub Actions и сами выкладываются на ваш VPS по SSH. Нужен только браузер — можно с iPhone. Mac и терминал на своём компьютере не нужны.

Один раз сделать 5 шагов (≈ 15 минут). Дальше каждое изменение в `main` выкладывается само, а при сбое сервер возвращается на прежнюю версию.

> Что понадобится: VPS с **Ubuntu 24.04** (2 ядра, 4 ГБ памяти — например, у российского хостинга или Hetzner Cloud CX22), доступ к его **веб-консоли** у провайдера и права администратора в репозитории на GitHub. Домен — по желанию: без него сервер получит адрес вида `203-0-113-10.sslip.io` с настоящим HTTPS-сертификатом.

---

## Шаг 1. Создать сервер

1. <https://console.hetzner.cloud> → проект → **Add Server**.
2. **Location** — любая в Европе; **Image** — **Ubuntu 24.04**; **Type** — **CX22** (или ARM **CAX11**).
3. **SSH keys** — можно не добавлять (ключ для деплоя создадим на самом сервере). Hetzner пришлёт пароль root на почту.
4. **Create & Buy now**. Запишите **IP-адрес** сервера (например `203.0.113.10`).

## Шаг 2. Создать отдельный ключ для деплоя — прямо на сервере

Ключ создаётся на сервере и нужен только GitHub для выкладки. Ваш личный доступ он не затрагивает.

1. В консоли Hetzner откройте сервер → вверху справа значок **>_ Console** (веб-консоль). Войдите как `root` с паролем из письма (при первом входе система попросит сменить пароль).
2. Вставьте по одной строке и нажмите Enter после каждой:

   ```bash
   ssh-keygen -t ed25519 -N '' -C github-deploy -f /root/.ssh/github_deploy
   cat /root/.ssh/github_deploy.pub >> /root/.ssh/authorized_keys && chmod 600 /root/.ssh/authorized_keys
   cat /root/.ssh/github_deploy
   ```

3. Последняя команда покажет **приватный ключ** — блок от `-----BEGIN OPENSSH PRIVATE KEY-----` до `-----END OPENSSH PRIVATE KEY-----`. Выделите его целиком вместе с этими строками и скопируйте. Это секрет `DEPLOY_SSH_KEY`.
4. Запомните отпечаток ключа сервера (пригодится в шаге 4):

   ```bash
   ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
   ```

   Строка вида `256 SHA256:AbCd… root@… (ED25519)`.

> Если копировать из веб-консоли неудобно, можно вывести ключ так: `cat /root/.ssh/github_deploy | tr '\n' '~'` и после вставки в секрет заменить `~` на переносы строк. Проще — скопировать как есть: GitHub принимает многострочные секреты.

## Шаг 3. Добавить секреты в GitHub

1. Репозиторий на GitHub → **Settings** → **Secrets and variables** → **Actions**.
2. Вкладка **Secrets** → **New repository secret**:

| Name | Значение |
| --- | --- |
| `DEPLOY_HOST` | IP-адрес сервера из шага 1 (например `203.0.113.10`) |
| `DEPLOY_SSH_KEY` | Приватный ключ из шага 2 целиком, включая строки `BEGIN` и `END` |
| `DEPLOY_USER` | необязательно: пользователь для входа (по умолчанию `root`; другой пользователь должен иметь `sudo` без пароля) |
| `DEPLOY_PORT` | необязательно: порт SSH (по умолчанию `22`) |

Названия — буква в букву.

## Шаг 4. Сначала — разведка (ничего не меняет)

1. Вкладка **Actions** → слева **deploy** → справа **Run workflow** → в поле **mode** оставьте `inspect` → **Run workflow**.
2. Через минуту откройте запуск → **Summary**: там отчёт о сервере — система, память и диск, занятые порты, Docker и его контейнеры, nginx/Caddy/Apache и их сайты (только имена), брандмауэр, автообновления, задачи cron (только имена), содержимое `/opt`. Секретов и содержимого файлов настроек в отчёте нет.
3. **Ключ сервера закреплён в репозитории** — файл `infra/deploy/known_hosts`; без закреплённого ключа выкладка не запустится. Делать ничего не нужно. Ключ нужно обновить, только если сервер переустановили или заменили: запустите `inspect`. В шаге **SSH key and host key** будет строка `Server host key (verify once)` с отпечатком `SHA256:…` и строки ключей под ней. Сверьте отпечаток с консолью провайдера (шаг 2.4). Если совпал — напишите Claude, он обновит файл (в каждой строке вместо адреса ставится `*`). Если не совпал — не продолжайте. Вместо файла можно задать переменную `DEPLOY_KNOWN_HOSTS` (**Settings → Secrets and variables → Actions → Variables**): если она задана, используется она.
4. Покажите отчёт Claude, если на сервере уже что-то работает (см. раздел ниже) — он подскажет настройки.

Разведка запускается только вручную и работает без включения выкладки.

## Шаг 5. Включить выкладку и запустить

1. **Settings → Secrets and variables → Actions → Variables → New repository variable**: имя `DEPLOY_ENABLED`, значение `true`. Это предохранитель: без него выкладка никогда не запускается.
2. **Actions → deploy → Run workflow** → **mode**: `deploy` → **Run workflow**.
3. Первый запуск идёт ≈ 10 минут: сборка образов, подготовка сервера, выкладка, проверка.
4. Откройте запуск → **Summary**: версия и режим (`direct` — Datascratch сам на портах 80/443; `edge` — рядом с Sinhron, через его Caddy; `proxy` — за вашим существующим веб-сервером, см. ниже).
5. **Адрес** сервера в журналах и Summary не показывается: репозиторий публичный, а сервер личный (D-49). Выкладка берёт его из секрета `DS_DOMAIN`, если он есть, иначе оставляет тот, с которым сервер уже работает, а на новом сервере без домена — адрес из IP. Без своего домена он такой: IP сервера с дефисами вместо точек + `.sslip.io` (IP `203.0.113.10` → `https://203-0-113-10.sslip.io`). Посмотреть на сервере: `/opt/datascratch/deploy.sh status` (строка `domain:`).

После этого каждый push в `main`, меняющий сервер, веб или инфраструктуру, выкладывается сам (пока `DEPLOY_ENABLED=true`).

## Сервер, на котором уже что-то работает

Datascratch умеет жить рядом с другими программами (например, вашим мессенджером) и ничего в них не меняет:

- **Docker.** Если Docker уже установлен (любой: `docker-ce` или `docker.io`), используется он; ничего не переустанавливается. Добавляется только недостающий модуль compose из того же источника.
- **Свои контейнеры отдельно.** Всё в отдельном проекте `datascratch`: контейнеры `datascratch-…`, тома `datascratch_…`, своя сеть. Чужие контейнеры, тома и сети не трогаются; никакой «очистки» (`docker system prune` и т. п.) не делается.
- **Брандмауэр.** Включённый `ufw` не меняется. Если Datascratch нужны порты 80/443, а `ufw` их закрывает, выкладка остановится с понятным сообщением — откройте их сами (`ufw allow 80/tcp && ufw allow 443/tcp`) или используйте режим за прокси. Если `ufw` выключен, а на сервере есть другие программы, Datascratch его **не включает** (это могло бы отрезать другие программы).
- **Автообновления** уже настроенные — не меняются; на сервере с другими программами их политика тоже не меняется.
- **Рядом с Sinhron.** Если на сервере работает Sinhron (контейнер `sinhron-caddy` держит 80/443), Datascratch встраивается в его Caddy: наш веб-контейнер `datascratch-web` не открывает портов, а подключается к общей docker-сети `edge`; выкладка кладёт файл `/etc/sinhron/caddy-sites/datascratch.caddy` (только свой) и перезагружает Caddy Sinhron — сначала `caddy validate`, при любой ошибке файл убирается и Caddy Sinhron не трогается. Сертификат для адреса Datascratch получает Caddy Sinhron. Заголовки безопасности Sinhron на Datascratch не распространяются (у веб-приложения свои).
  - Нужна версия Sinhron, которая умеет принимать соседей (импортирует `/etc/caddy/sites/*.caddy` и подключена к сети `edge`). Если Sinhron старее, выкладка остановится с сообщением «Update Sinhron first» — обновите Sinhron (`sudo bash /opt/sinhron/server/install.sh --yes --no-upgrade`; это делает его владелец, Datascratch сам Sinhron не обновляет) и запустите выкладку снова.
- **Порты 80/443 заняты другим веб-сервером** (не Sinhron) — Datascratch слушает только `127.0.0.1:8480` (снаружи недоступен), а HTTPS и сертификат остаются за вашим веб-сервером. Готовые настройки лежат на сервере: `/opt/datascratch/proxy/nginx.conf`, `Caddyfile` и `traefik.yml` (в Summary их нет — в них адрес).
  - **nginx, вручную (по умолчанию):** скопируйте `/opt/datascratch/proxy/nginx.conf` в `/etc/nginx/sites-available/datascratch.conf`, затем `ln -s /etc/nginx/sites-available/datascratch.conf /etc/nginx/sites-enabled/ && nginx -t && systemctl reload nginx`. Сертификат: `certbot --nginx -d <адрес сервера>`.
  - **nginx, автоматически:** переменная `DS_NGINX_AUTO=true` — выкладка сама добавит этот сайт (только свой файл `datascratch.conf`; прежняя версия этого файла сохраняется рядом), проверит `nginx -t` и перезагрузит nginx. Если проверка не прошла — всё возвращается как было, nginx не перезагружается. С `DS_NGINX_CERTBOT=true` дополнительно запустится `certbot --nginx` для адреса Datascratch.
  - **Caddy / Traefik:** добавьте фрагмент из `/opt/datascratch/proxy/Caddyfile` или `traefik.yml` — сертификат они получат сами.
- **Память.** Если на сервере есть другие программы, Datascratch берёт меньше: PostgreSQL до 512 МБ, сервер до 512 МБ, веб до 128 МБ (вместо 1 ГБ / 1 ГБ / 256 МБ) — не больше 1,15 ГБ, в простое 300–400 МБ. Вместе с Sinhron (≈ 1–1,5 ГБ) остаётся запас на 4 ГБ. Проверено замером (`infra/deploy/test/memory-check.sh`): первая синхронизация 10 000 заметок с этими лимитами — пик PostgreSQL ~50 МБ, сервер ~110 МБ, веб ~11 МБ, без перезапусков.

Настройки (переменные репозитория, все необязательные):

| Имя | Значение |
| --- | --- |
| `DEPLOY_MODE` | `auto` (по умолчанию: рядом с Sinhron, если он есть; иначе за прокси, если 80/443 заняты; иначе сам на 80/443), `standalone` — сам на 80/443, `behind-proxy` — за Sinhron или другим веб-сервером |
| `DS_PROXY_PORT` | порт на `127.0.0.1` в режиме за прокси (по умолчанию `8480`) |
| `DS_NGINX_AUTO` | `true` — добавить сайт в существующий nginx (с проверкой и откатом) |
| `DS_NGINX_CERTBOT` | `true` — вместе с этим получить сертификат через certbot |
| `DS_HOST_MODE` | `auto` (по умолчанию), `shared` — считать сервер общим, `fresh` — пустым |
| `DS_MEM_PROFILE` | `auto` (по умолчанию), `full`, `shared` — лимиты памяти |

## Что происходит на сервере

| Что | Где |
| --- | --- |
| Всё приложение | `/opt/datascratch` (`docker-compose.yml`, `.env`, скрипты) |
| Секреты (пароль базы, `DS_KMS_KEY`, ключи токенов) | `/opt/datascratch/.env` — создаются **один раз на самом сервере**, в GitHub и в логи не попадают; при следующих выкладках не меняются |
| Брандмауэр | на пустом сервере — `ufw` с портами 22, 80, 443; существующие настройки не меняются |
| Обновления безопасности Ubuntu | на пустом сервере включаются автоматически; существующие настройки не меняются |
| Резервные копии | каждую ночь в 03:17 → `/opt/datascratch/backups/`, хранятся 14 дней |
| Адрес | веб-приложение, API (`/v1`), синхронизация (WebSocket) и подключение ИИ-агентов (`/mcp`) — на одном домене; метрики наружу не отдаются |

**Сохраните `DS_KMS_KEY`.** Первая установка сообщает в журнале выкладки, что ключ создан, но сам ключ туда не выводит: журнал GitHub Actions виден всем. Зайдите на сервер по SSH (или через веб-консоль провайдера) и выполните `/opt/datascratch/ds key`. Команда объяснит, для чего ключ, и покажет его. Сохраните ключ в менеджер паролей, затем выполните `/opt/datascratch/ds key-saved`, чтобы команды `ds` перестали напоминать. Ключ нужен блокнотам в режиме «для агентов» и специально не входит в резервные копии. Если его потерять, ИИ-агенты не откроют такие блокноты, пока вы не выключите и снова не включите для каждого режим «для агентов» в приложении. Сами заметки при этом не пострадают.

## Бэкап и переезд

Копии делает и хранит администратор сервера (D-55). Внешних хранилищ и кнопок в GitHub для этого нет. Все команды выполняются на сервере, по SSH, от `root`:

| Что | Команда |
| --- | --- |
| Сделать копию сейчас | `/opt/datascratch/ds backup` — покажет файлы копии и их размер |
| Список копий | `/opt/datascratch/ds backups` |
| Восстановить из копии | `/opt/datascratch/ds restore db-ДАТА.dump` — спросит подтверждение (`yes`), сначала проверит копию и сохранит текущие данные в `pre-restore-ДАТА.*` (если что-то пошло не так, их можно восстановить той же командой) |

Ночные копии делаются сами, каждую ночь в 03:17, и хранятся 14 дней в `/opt/datascratch/backups/`. Копия — это два файла: база `db-ДАТА.dump` и вложения `files-ДАТА.tar.gz`.

**Унести копию с сервера** (на свой компьютер или другой сервер), например:

```bash
scp root@АДРЕС-СЕРВЕРА:/opt/datascratch/backups/*-ДАТА.* .
# или все копии сразу, повторный запуск докачивает только новые:
rsync -av root@АДРЕС-СЕРВЕРА:/opt/datascratch/backups/ ./datascratch-backups/
```

**Переезд на новый сервер:**
1. На старом сервере: `/opt/datascratch/ds backup` и скопировать оба файла себе (`scp`, как выше). Сохранить `/opt/datascratch/.env` или хотя бы `DS_KMS_KEY` из него.
2. Новый сервер: шаги 1–5 этой инструкции (в GitHub поменять `DEPLOY_HOST` и ключ сервера, шаг 4.3). Выкладка поставит пустой Datascratch.
3. Вернуть ключ: в `/opt/datascratch/.env` нового сервера заменить значение `DS_KMS_KEY` на сохранённое. Остальные секреты можно оставить новыми.
4. Скопировать файлы копии на новый сервер в `/opt/datascratch/backups/` (`scp db-ДАТА.dump files-ДАТА.tar.gz root@НОВЫЙ-СЕРВЕР:/opt/datascratch/backups/`) и выполнить `/opt/datascratch/ds restore db-ДАТА.dump`.
5. Если домен свой — переключить у регистратора запись **A** на IP нового сервера, и через 5–30 минут приложения сами продолжат работать. Если адрес изменился (например, новый `…sslip.io`), в приложениях ввести новый адрес сервера на экране входа (D-49), новой сборки не нужно. Ссылки шеринга со старым адресом нужно будет пересоздать.

## Какие адреса в интернете нужны серверу

Сервер ничего не скачивает с Docker Hub (из России он бывает недоступен): все образы, включая PostgreSQL, GitHub заранее перекладывает в свой реестр GHCR. Docker ставится из обычного репозитория Ubuntu. Серверу нужен доступ только к:

| Адрес | Зачем |
| --- | --- |
| `ghcr.io`, `pkg-containers.githubusercontent.com` | Скачать образы Datascratch при выкладке |
| Зеркало пакетов Ubuntu (обычно у хостинга, например `mirror.*` или `archive.ubuntu.com`, `security.ubuntu.com`) | Docker, брандмауэр, обновления безопасности |
| `acme-v02.api.letsencrypt.org` | Получить и продлевать HTTPS-сертификат |
| `sslip.io` (DNS) | Адрес без своего домена: `203-0-113-10.sslip.io` → ваш IP; используется браузерами и Let's Encrypt, сам сервер к нему не обращается |

Входящие подключения: SSH (22) — от GitHub Actions для выкладки, 80 и 443 — от пользователей и Let's Encrypt.

Если GHCR когда-нибудь окажется недоступен с сервера, Claude может переключить выкладку на зеркало `mirror.gcr.io` — напишите об этом.

## Память

Рассчитано на VPS с 2 ядрами и 4 ГБ. На пустом сервере: PostgreSQL ограничен 1 ГБ (`shared_buffers` 256 МБ), сервер — 1 ГБ, Caddy — 256 МБ; остальное — системе и кэшу диска. В простое всё вместе занимает около 400–500 МБ.

## Если выкладка не удалась

- Сервер **сам возвращается на предыдущую версию**, если новая не запустилась или не прошла проверку. Данные не трогаются.
- Красный крестик в Actions → откройте запуск, шаг с ошибкой подскажет причину. Частые:
  - `Missing secrets` (запуск пропущен, зелёный) — не добавлены `DEPLOY_HOST` / `DEPLOY_SSH_KEY`;
  - `not a valid private key` — секрет скопирован не целиком (нужны строки `BEGIN` и `END`);
  - `Server unreachable` — сервер выключен или закрыт порт SSH;
  - `Host key verification failed` — у сервера сменился ключ (переустановка): запустите `inspect`, сверьте новый отпечаток с консолью провайдера и обновите `infra/deploy/known_hosts` (шаг 4.3).
  - `No pinned host key` — нет ни файла `infra/deploy/known_hosts`, ни переменной `DEPLOY_KNOWN_HOSTS`: шаг 4.3.
- Откатить вручную: веб-консоль сервера → `/opt/datascratch/deploy.sh rollback`. Текущее состояние: `/opt/datascratch/deploy.sh status`.
- Изменения базы данных (миграции) только добавляют новое, поэтому откат на предыдущую версию безопасен.

## Подключить свой домен (по желанию)

1. У регистратора домена создайте запись **A**: имя, например, `notes` → IP сервера. Подождите 5–30 минут.
2. GitHub → **Settings → Secrets and variables → Actions → Secrets** → **New repository secret**: имя `DS_DOMAIN`, значение `notes.ваш-домен.ru`. Именно секрет: переменные видны в публичных журналах, и переменную `DS_DOMAIN` выкладка больше не читает. Без секрета сервер просто остаётся на своём нынешнем адресе (выкладка берёт его с сервера), поэтому уже заведённую переменную трогать не обязательно.
3. **Actions → deploy → Run workflow**. Caddy сам получит сертификат для нового домена. Старый адрес `…sslip.io` перестанет обслуживаться — войдите в веб-приложении по новому адресу. Ссылки шеринга, созданные на старом адресе, нужно будет пересоздать.

## Адрес сервера для iPhone и iPad

Адрес в сборку не зашивается (D-49): при первом входе приложение спрашивает адрес сервера (или берёт его из ссылки-приглашения). Новая сборка при смене адреса не нужна.

**Ссылки сразу в приложении (Universal Links).** Приглашения (`/invite/…`) и ссылки шеринга (`/s/…`) на iPhone и iPad открываются прямо в приложении. Для этого сервер отдаёт `https://<адрес>/.well-known/apple-app-site-association`: только эти два вида ссылок, всё остальное открывается в браузере. Настраивать ничего не нужно — выкладка берёт Team ID из того же секрета `APPLE_TEAM_ID`, что и выпуск iOS, а сборка для TestFlight узнаёт адрес сервера сама (`infra/deploy/web-host.sh`, по SSH, в журнале не показывается). Если адрес меняется, после переезда нужна новая сборка: ссылки привязаны к адресу в сборке.

Веб-приложению ничего настраивать не нужно: оно открывается с того же адреса и само обращается к API на нём же.
